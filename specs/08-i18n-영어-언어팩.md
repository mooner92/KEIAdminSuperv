# Spec 08 — 영어 언어팩(i18n) · 글로벌 페이지 관리

> ⛔ **미착수 · 보류**(2026-07-28 사용자 결정). 착수 안 함 —
> ⓐ 콘텐츠(법령·규정) 번역은 **오역 위험**이 절대규칙 1(내용 지어내기 금지)과 충돌하고,
> ⓑ UI만 영어로 바꾸면 "메뉴는 영어, 답은 한국어"라 실사용자(KEI 직원)에게 가치가 없다.
> ⓒ 포트폴리오 목적이었다면 한국어 UI인 채로가 오히려 강하다(실조직·실사용 증거).
> 계획은 그대로 둔다 — 외국인 연구원 실유입 등 조건이 바뀌면 이 문서에서 재개.

> 2026-07-28 사용자 요청: "영어 매칭 언어팩 같은 걸로 영어 버전으로 볼 수 있게 글로벌 페이지
> 관리를 하고 싶다. dev/apply/en 같은 브랜치로 진행할까?"
> 실측: UI 한국어 문자열 조각 **~4,176개 / 82파일**(근사) · 영문 콘텐츠는 정관(영문) 1건뿐.

## 0. 먼저 정해야 하는 것 — 이 앱에서 "영어 버전"의 정직한 범위

세 층이 완전히 다른 문제다. 섞으면 망한다.

| 층 | 번역 가능? | 방법 |
|---|---|---|
| **① UI 크롬**(내비·버튼·라벨·빈상태·안내문) | ✅ 언어팩으로 가능 | 이 스펙의 본체 |
| **② 콘텐츠**(규정 원문·가이드·용어집 688문서) | ⛔ **불가** | 원문 의역 금지(절대규칙 2). 영문본은 정관(영문) 1건뿐 — 번역은 별도 사업 |
| **③ LLM 답변** | ⚠ 보류 | 한국어 코퍼스 근거로 영어 답변 생성은 가능하나 **가드레일·채점 전체가 한국어 전제** — Phase 4에서 별도 결정 |

⟹ **v1 목표: "영어 UI + 한국어 콘텐츠"**. 영어 모드에서도 문서·답변은 한국어로 나오고,
그 사실을 UI가 정직하게 고지한다("Documents and answers are in Korean"). 외국인 방문연구원이
화면 구조를 이해하고 탐색할 수 있게 하는 것이 v1의 가치다.

## 1. 기술 선택 — ⚠ Next 내장 i18n은 못 쓴다

- 이 앱은 `output: "export"`(정적 export) — **Next.js i18n 라우팅(`/en/*` locale 라우트)은
  정적 export 미지원**(공식 제약). 서버 런타임 도입은 배포 구조(server.js 게이트)를 흔들므로 기각.
- ⟹ **런타임 사전 전환**(테마와 동일 패턴): 단일 라우트 + 클라이언트 언어 상태.
  - `web/lib/i18n.tsx` — `LangProvider`(pref `ko|en`, localStorage `kei-lang`, 기본 ko) +
    `useT()` 훅. `<html lang>` 동기화(접근성).
  - 사전: `web/locales/ko.ts` = **정본(키 = 실제 한국어 문장)** / `en.ts` = 매핑.
    `t("문서 찾기")` → en이면 "Find Documents", 키 미존재 시 **한국어 폴백**(빈 화면 사고 방지).
    키를 영문 식별자가 아니라 한국어 원문으로 쓰는 이유: 4,176개 조각을 식별자로 개명하는
    작업량이 본 작업보다 크고, 누락 시 폴백이 자연스럽다.
  - 토글: 상단바(테마 토글 옆) `한/EN` — flag `i18n_en`(release)으로 노출 게이트.

## 2. 단계 (PR 분할)

| Phase | 내용 | 규모 |
|---|---|---|
| **P0** | 문자열 인벤토리 스크립트(`web/scripts/i18n-scan.mts`) — JSX 텍스트·placeholder·aria·title 추출 → `locales/ko.ts` 초안 자동 생성 + **미치환 잔존 스캔**(회귀 도구 겸용) | 0.5일 |
| **P1** | `lib/i18n.tsx` + 셸부터 치환(Layout 사이드바·상단바·라이브러리·푸터) + 토글 + flag | 0.5일 |
| **P2** | 핵심 화면 순차 치환: 채팅(빈화면·컴포저·근거 패널·면책) → 문서 찾기(필터·칩·배지) → 업무 도구 → 결재선·캘린더·기한 | 2~3일 |

## 3. 지키는 것 (이 레포 특유의 함정)

1. **콘텐츠·데이터 키 불변** — 섹션 키(`규정집`)·볼트 본문·slug·검색 인덱스는 그대로. 표시만 매핑
   (07-27 워딩 개선과 같은 수술법).
2. **거부 정본·채점기 무접촉** — `refusal_detect`·SYSTEM 프롬프트는 한국어 전제. UI 언어팩은
   여기 닿지 않는다(P5 전까지 답변은 한국어).
3. **패치노트·의견함은 한국어 유지** — 내부 운영 채널. EN 모드에선 원문 그대로 노출(고지 문구만 영어).
4. CLAUDE.md "사용자 노출 콘텐츠는 한국어" 규약을 "기본 한국어 + EN 언어팩(UI 한정)"으로 개정.

## 4. P5(LLM 영어 답변)를 보류하는 이유 — 나중에 논의할 자료

- SYSTEM 규칙·수치 게이트·거부 정본·`refusal_detect`·일일 채점이 전부 한국어 표층에 묶여 있다.
  영어 답변을 열면 **품질 측정 체계 전체를 이중화**해야 한다(T7·T9류 사고의 영어판 위험).
- 근거 인용(`[규정명 제N조]`)은 한국어 규정명 그대로 남는다 — 영어 답변 속 한국어 인용의 UX도 애매.
- 열게 되면: 답변 언어 파라미터 → SYSTEM에 "answer in English, cite Korean titles verbatim" +
  영어 거부 정본 신설 + 평가에서 EN 답변 분리 집계. 별도 스펙으로.

## 5. 브랜치 — `dev/apply/en` 대신 기존 규칙으로

docs/60 명명(`feat|fix|chore/<케밥>`)을 따르는 게 맞다: **`feat/i18n-en`** (dev에서 분기).
- `dev/apply/en` 같은 신설 네임스페이스는 훅·워크트리 관례와 어긋나고, 언어팩은 "영구 분기"가
  아니라 **한 번 병합되면 끝나는 기능**이다(영어 전용 브랜치를 계속 유지하면 두 벌 관리 지옥).
- 롤아웃은 브랜치가 아니라 **flag `i18n_en`**이 담당(off 배포 → dev 검증 → on) — 이 레포의
  표준 릴리스 경로.
