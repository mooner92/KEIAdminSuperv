# Spec 12 — 품질 분석 자동화 3단(분석서 → LLM 진단 → 자동 개선)

> 2026-08-03 · 운영자 요구: "이거 분석도 자동화 해야 할 것 같은데, 아침마다 분석서를 발급할 수
> 있나? 분석하고 개선 작업까지 가능한가?"
> 관련: docs/58(자가평가) · specs/11(어휘 갭) · docs/52(오토픽스 Phase A) · docs/66(알림).

## 0. 무엇이 문제였나

채점은 매일 자동인데 **해석은 매번 사람이 손으로** 했다. 2026-08-03에도 즉석 파이썬으로
어휘 갭·검색실패율을 계산했고, 08-01 약점 매트릭스도 즉석 계산이었다. 같은 계산을 매번
다시 짜는 것은 자동화가 아니라 **반복**이다.

## 1. 왜 "작업 예약"이 답이 아닌가 (조사 결과)

세션 예약 도구(CronCreate)는 **세션 한정**이다: 디스크에 안 남고, 세션이 끝나면 사라지며,
반복 작업은 7일 뒤 만료된다. 매일 아침 발급에는 못 쓴다.
정답은 **이미 쓰고 있는 두 부품을 잇는 것**이다 — OS 크론(`daily_run.sh`)과 무인 Claude
Code(`tools/maint_executor.py`: 격리 worktree·결정적 관문·월 예산 상한, 제보 자동수정용).

## 2. 3단 구조 (각 단이 독립적으로 유용해야 한다)

| 단 | 무엇 | LLM | 실패하면 | 상태 |
|---|---|---|---|---|
| 1 | 결정적 분석서 — 수치·분류·행동 후보 | ❌ | 크론 계속 | **완료(2026-08-03)** |
| 2 | LLM 진단 — "왜 틀렸나 / 뭘 먼저 고치나" | ✅ 읽기만 | 1단이 남는다 | 설계 |
| 3 | 자동 개선 — 브랜치 push, 머지는 사람 | ✅ 쓰기 | 2단이 남는다 | 설계 |

⛔ **아래 단이 위 단 없이도 성립해야 한다.** 2단이 죽어도 1단 분석서는 매일 나오고,
3단이 꺼져도 2단 진단은 남는다. 자동화가 늘수록 신뢰해야 할 대상이 늘어나는 구조는 안 만든다.

## 3. 1단 — 완료분 기록

`eval/daily_report.py`(LLM 0회) → `web/public/quality/reports/<date>.{md,json}`.
핵심은 **'수술 대기'와 '측정 노이즈'의 분리**다:

- 수술 대기 = 검색실패·생성환각 → 서비스가 실제로 못 한 것
- 측정 노이즈 = 출제결함·골든품질·판정불가 → 시험지가 이상했던 것

08-03 실측으로 말하면 "오답 21건"이 아니라 **"고칠 것 9건 + 시험지 손볼 것 21건"**이다.
섞어 보면 매일 수십 건짜리 목록이 쌓이고 아무도 안 본다.

포함: 코호트(재시험이 낮은 건 정상이라는 고정 문구 포함) · 어휘층 표와 갭 · 짝 불일치 ·
검색실패가 몰린 규정 · 약점 주제 · **근거 수치를 단** 행동 후보.
배선: `daily_publish` → `daily_report` → prod 동기화(순서 중요 — 뒤에 두면 하루 늦게 간다) ·
Slack 다이제스트 한 줄에 `어휘갭 N%p · 🔧수술대기 N건` 추가(새 알림 종류 없음 — docs/66 규율).
회귀: `eval/test_daily_report.py` 6종(합성 픽스처).
부수 성과: 도입 첫 실행에서 패러프레이즈 자족성 게이트 누락을 잡아냈다(specs/11 A1 보강).

## 4. 2단 — LLM 진단 (설계)

**입력**: 1단의 `reports/<date>.json` + 해당 문항의 답변·근거(로컬 파일). ⛔ 사용자 채팅 미열람.
**출력**: `reports/<date>.diagnosis.md` + 🔔/Slack 한 줄(제목만). 코드 변경 없음.

### 4.1 진단이 답해야 할 질문 (프롬프트의 뼈대)

1. 수술 대기 N건을 **원인별로 묶어라** — 같은 규정? 같은 어휘? 같은 실패 방식?
2. 각 묶음에 **가장 싼 가설 하나**와 그것을 확인할 방법을 써라.
3. **오늘 하지 말아야 할 것**도 써라(표본 부족·1회성 노이즈).
4. 근거 없는 추정에는 "확인 필요"를 붙여라 — ⛔절대규칙 1의 평가판.

### 4.2 실행 골격 (maint_executor 재사용)

- 구독 인증 무인 Claude Code, **읽기 전용 도구셋**(Bash 미부여 — 오토픽스와 동일 정책).
- 격리 worktree에서 실행(레포 오염 방지), 산출물은 파일 1개.
- 월 예산 상한 공유(`AUTOFIX_BUDGET_USD`) — 진단이 예산을 다 먹으면 3단이 굶는다.
- 트리거: `daily_run.sh` 마지막 단계(`|| true`) + 관리자 화면의 "지금 진단" 버튼.

### 4.3 검증 방법 (이게 없으면 2단은 도입하지 않는다)

진단이 **맞는지**를 사람이 매일 채점할 수는 없다. 대신 둘을 본다:
- ⓐ 진단이 지목한 규정/조문이 실제로 그날 수술 대기에 있었는가(결정적 대조 — 스크립트).
- ⓑ 2주 뒤, 진단이 제안한 조치가 적용된 항목의 재시험 정답률이 올랐는가(추적).
ⓐ가 자주 틀리면 2단은 끈다. **틀린 진단은 없는 진단보다 나쁘다** — 사람이 그걸 믿고 움직인다.

## 5. 3단 — 자동 개선 (설계, 조건부)

`maint_executor` 경로 그대로: 격리 worktree → 결정적 관문 → `autofix/eval-<date>` 브랜치
push + compare URL 🔔. ⛔ 라이브 무접촉·머지는 사람.

### 5.1 ⛔ 이 프로젝트 특유의 위험 — 시험을 쉽게 만들기

평가 파이프라인을 고칠 권한을 주면, 가장 쉬운 "개선"은 **점수가 오르게 채점을 바꾸는 것**
이다(임계값 완화, 어려운 문항 폐기, 골든 느슨하게). 그래서 3단의 금지구역은 오토픽스보다
넓다 — `FORBIDDEN_PATHS`에 다음을 추가한다:

- `eval/daily_grade.py` · `eval/axes.py` · `eval/gen_filter.py`(게이트·임계값)
- `eval/question_bank.jsonl`(골든) · `eval/daily_report.py`(분류 기준)
- `tools/rag_core.py`의 SYSTEM 가드레일(이미 AST 비교로 방어 중)

즉 3단이 만질 수 있는 것은 **서비스 쪽**(검색 라벨·별칭 사전·볼트 가이드 문서)이지
**측정 쪽**이 아니다. 이 경계가 3단 도입의 전제 조건이다.
