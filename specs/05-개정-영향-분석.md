# Spec 05 — 개정 영향 분석 (Change Impact Analysis)

> 2026-07-26 · 사용자 방향: "행정 초보용을 넘어 행정 업무를 깊이 파고드는 레벨로" — 벤치마킹
> (정부 AI 법령 비서·해외 정책관리 SW의 change impact analysis) 결과 1순위로 선정.
> **추가 데이터 수집 0** — 이미 만들어둔 3개 인덱스를 화면·답변으로 승격하는 작업.

## 0. 왜 이것인가

- 대상 사용자 확장: 행정 **초보**(어떻게 하지?) → **규정 담당자·중간관리자**(이 개정이 어디에 미치나?)
- 해외 정책관리 SW의 표준 기능("regulatory updates → flags which policies need revision") —
  우리는 그 원료(조문 그래프)를 이미 갖고 있으면서 드로어 배지 수준으로만 쓰는 중.
- 실증 수요: 이본·낙후 19건(conflict_audit)의 근본 원인이 "개정이 파생 문서에 전파되지 않음" —
  이 기능은 그 전파를 **사전에 보이게** 한다.

## 1. 딛고 서는 데이터 (전부 기존 자산, 2026-07-26 실측)

| 인덱스 | 내용 | 규모 |
|---|---|---|
| `article_status.json`(01k) | 조문별 효력·개정 시계열·검수상태 | **1,943 조문** |
| `clause_xref.json`(01i) | 조문↔조문 준용·인용 엣지(scope: self/cross) | 규정 전역 |
| `graph_analytics.json`(01l) | **개정 파급(impact)** = reverse 전이폐포 · 공동인용 | impact 18규정 |
| `byeolji_manifest`·`refs` | 조문→별표/서식 연결 | 288 별지 |
| `deadlines.json`(01m) | 조문→기한 | 57건 |
| `approval.json`(01n) | 위임전결(별표) 규칙 | 335건 |

⚠ 한계 실측: `graph_analytics.impact`가 **규정 단위**(18개)로만 집계돼 있다 — 조문 단위 파급은
`clause_xref`에서 즉석 계산해야 한다(01l 확장 또는 API에서 BFS).

## 2. 사용자 스토리

1. **개정 검토** — "복무규정 제14조를 고치려 한다" → 이 조를 준용·인용하는 조문 N개, 이 조를 근거로
   한 가이드 문단·별지 서식·기한·전결 규칙이 한 화면에.
2. **개정 후 점검** — "6월에 직원평가규칙이 개정됐다" → 파생 문서(세부기준 2종·길라잡이) 중
   **아직 옛값을 인용 중인 곳** 후보 목록(이본 17건 사태의 재발 방지).
3. **챗봇 연동** — "인사규정 제31조 바뀌면 뭐가 영향받아?" 를 채팅에서 물으면 동일 데이터로 답변
   (결정적 조회 — LLM은 서술만, 목록은 인덱스에서).

## 3. 설계

### 3-1. 데이터 계층 — `01l` 확장 (조문 단위 파급)
```
python tools/01l_graph_analytics.py  # 기존 실행 그대로, 산출 확장
```
- `impact_by_article`: `{ "규정명#제N조": { direct: [피인용 조문…], transitive: […], guides: [가이드 문단 anchor…], forms: [별지…], deadlines: […], approval: [업무 키…] } }`
- 소스: clause_xref(cross 엣지 역방향 BFS, 깊이 ≤3·순환 가드) + 01b 위키링크(가이드→조문) +
  byeolpyo refs + deadlines의 조 매핑 + approval 원문행의 규정 참조.
- ⛔ **원문 불변·읽기 전용** — 파급 목록은 "확인해야 할 후보"이지 "고쳐야 할 목록"이 아니다(단정 금지,
  화면 문구에 명시).

### 3-2. 화면 — `/impact` (업무 도구 허브 카드 추가)
- 진입: ① 규정·조문 검색(공용 SearchInput) ② 문서 드로어의 기존 `graph_impact` 칩에서 "전체 보기 →"
- 구성(공용 컴포넌트 계약 준수 — BrowseShell + FilterGroup + ResultList/ResultRow + PagedList):
  - 좌: 규정 필터(패싯 카운트) · 영향 유형 필터(조문/가이드/서식/기한/결재선)
  - 우: 선택 조문 카드(현행 효력·최근 개정일 — article_status) + 영향 목록(유형 칩·근거 링크 →
    문서 드로어). 파급 깊이 1/2/3 토글(기본 1).
- **개정 후 점검 모드**: `article_status`의 최근개정일 기준 "최근 90일 개정 조문" 목록 → 각 조문의
  파급 대상 중 개정일이 그보다 **오래된** 파생 문서를 ⚠후보로 배지(= 낙후 의심).
- 플래그: `impact_analysis`(FLAG_REGISTRY + lib/flags 기본 off → dev 검증 후 on).

### 3-3. 챗봇 연동 (결정적 자동첨부 — defterm_route와 동형)
- 감지: `(규정명|제N조).*(바뀌|개정|영향|파급)` 패턴 → `impact_by_article` 조회 결과를 근거 블록으로
  첨부(`impact_route` 배지). LLM은 목록을 **요약 서술만**(목록 자체는 결정적 — 환각 0).
- 토글 `RAG_IMPACT_ROUTE`(기본 off — 골든 A/B 후 on).

## 4. 검증 관문 (관례 그대로)
1. 유닛: BFS 순환·깊이 가드, 알려진 사례 재현 — "직원평가규칙(3210) 개정 → 세부기준 2종이 후보로
   떠야"(conflict_audit ⓑⓒ 실사례를 회귀 케이스로).
2. 회수 A/B: impact_route on/off 골든 100 비퇴행(신뢰 게이트 6/6 포함).
3. 실렌더: verify-impact.mjs(검색→조문 선택→유형 필터→드로어 진입, 공용 컴포넌트 클래스 단언).
4. 정확성 표본: 파급 후보 10건 수작업 대조(가짜 엣지 비율 기록 — 과탐은 허용, 누락은 기록).

## 5. 작업 순서(예상 1~1.5일)
| 단계 | 산출 |
|---|---|
| D1 | 01l 확장(impact_by_article) + 유닛 + 실사례 회귀 |
| D2 | /impact 화면(공용 컴포넌트) + 드로어 연결 + 플래그 |

## 6. 명시적 비목표

- 자동 수정·자동 검수 — 후보 제시까지(⛔ 사람 확정 원칙).
- 외부 법령 개정 모니터링 — law.go.kr 증분은 docs/61 후속(별개 트랙).
