# 16. Qwen3.5-9B `reasoning_effort` A/B — `none` vs `low`

> 트러블슛/의사결정 기록. **결론: 현행 `reasoning_effort="none"` 유지.**
> 측정일 2026-07-05~06 · dev(3101/9001) 격리 환경 · N=223 값문항 · 총 20,407초(약 5.7시간).
> 원자료(질문·답변·규정 파생물)는 `eval/reports/reasoning-ab-0705/`(gitignore)에 로컬 보관 — 이 문서는 **집계치만**.

## TL;DR

Qwen3.5는 "사고(thinking) 모델"이라, **사고를 조금 켜면(`low`) 금액·일수 계산 정확도가 오를까?** 를 검증했다.
동일 검색근거로 `none`(현행·사고 off)과 `low`(짧은 사고)를 값문항 223개에 A/B한 결과:

- **정확도**: `low`가 **오히려 나쁨** (평균 값일치 0.620 → **0.529**). 문항별 승부도 `none` 42승 vs `low` 14승(무승부 167).
- **지연**: `low`가 **4.8배 느림** (중앙 14.6s → **70.5s**). 사고에 평균 ~9,900자를 소비.
- **출처 인용**: `low`가 **떨어짐** (0.919 → 0.740). 사고에 예산을 쓰고 최종 답이 짧아지며 출처를 빠뜨림.
- **모든 버킷·여비 계산 서브셋에서 `low`가 열세.**

→ **사고 on은 우리 RAG(추출형 과제 + Vulkan 저속 + 스트리밍 UX)에 이득이 없고 손해만 크다. `none` 유지.**

## 왜 테스트했나

계산이 필요한 질문(여비 = 일비·식비·숙박 상한 × 일수/박수)에서, 모델이 머릿속으로 단계를 정리하면
값 실수가 줄지 않을까 하는 가설. 현행은 사고를 완전히 끄고(`reasoning_effort="none"`), 대신 SYSTEM 프롬프트
규칙 10으로 "계산 과정을 **답변에** 단계로 드러내라"고 지시한다. 절충안으로 `low`(짧은 사고)가 나은지 확인.

## 방법 (순수 비교)

- **표본**: 기준선 감사(`qwen3-audit-0703`)의 값문항(핵심 수치 있음) **223개**. 버킷: 규정_수치 148 · 가이드 48 · 별표 26 · ERP 1.
- **통제**: 문항마다 **검색을 1회만** 수행(동일 근거)하고, 그 근거를 두 팔에 똑같이 주입. **차이는 오직 `reasoning_effort`**(none/low). 온도·프롬프트·모델 동일.
- **환경**: dev 격리 — Qwen3.5-9B(격리 Ollama 11436, Vulkan), 검색 근거는 리랭커 포함. 답변은 prod와 동일한 후처리(사고블록 제거·공백정규화·면책 보장) 후 채점.
- **채점**(감사 스크립트 재사용): 값일치율(핵심 수치가 답변에 실제 등장) · 인용 · 거부 · 면책 · CJK(중/일 문자) 오염 · 지연.

## 해석 — 왜 `low`가 더 나쁜가

1. **과제가 추출형이다.** 답의 값은 [근거]에 이미 있다. 필요한 건 "표에서 옳은 칸을 골라 옮기기"이지 다단계 추론이 아니다. 사고는 여기서 가치를 못 더한다.
2. **사고가 값을 흔든다.** 긴 사고(평균 ~9,900자) 중 모델이 스스로 옳게 뽑은 값을 재검토하다 **틀린 쪽으로 말을 바꾸는** 경우가 관측됨(전량누락 62→87 증가).
3. **출력 예산 잠식.** 사고에 토큰을 쓰고 최종 답이 짧아져(671→409자) **출처·수치를 빠뜨린다**(인용 0.919→0.740).
4. **Vulkan 저속.** 드라이버 535로 CUDA 불가 → 사고 토큰이 2~3배로 늘면 체감 지연이 폭증(중앙 14.6→70.5초). 스트리밍 채팅 UX에 치명적.

계산 투명성(단계 노출)은 **사고를 켜지 않고도** SYSTEM 규칙 10(계산식·근거조문을 답변에 단계로)으로 이미 확보하고 있다.
