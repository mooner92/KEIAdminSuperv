# 23. 로우레벨 지렛대 — 표 복원 · 검색기 파인튜닝 · 수치 스토어

> 배경: "전 문서 과학습 파인튜닝으로 수치 오류를 없애자"는 구상을 3렌즈 리서치로 검증한 결과
> **반박됨**(요지는 §0). 대신 같은 목표(수치 정확도)를 문헌·하드웨어 제약에 부합하게 달성하는
> 세 지렛대를 정의한다. ⛔ 절대 규칙 유지: 원문 의역 금지·검수상태 자동변경 금지·온프레미스.

## 0. 왜 LLM 파인튜닝이 아닌가 (리서치 요지, 출처는 워크플로 산출물)

- **역효과 입증**: 파인튜닝으로 새 사실을 주입할수록 환각이 선형 증가(Gekhman et al., EMNLP 2024).
  지식주입 정면 비교에서 RAG ~0.88 vs FT ~0.50 (Ovadia et al., EMNLP 2024). 사실 암기에는
  사실당 ~1,000회 노출 필요(Allen-Zhu & Li, ICLR 2025) — 규정 개별 수치는 몇 회뿐이라 구조적 불가.
- **부작용**: 좁은 코퍼스 과학습 → catastrophic forgetting + instruction-following(가드레일 순응) 저하.
  암기 강화 → 개정 후 RAG 근거와 충돌 시 옛 값 고집(knowledge conflict, ICLR 2024).
- **하드웨어**: Quadro RTX 6000=Turing(CC 7.5) → bf16 미지원(Unsloth Qwen3.5 가이드는 bf16 전제),
  Mamba계 Triton 커널 공식지원 CC 8.0+, 9B LoRA 22GB vs 24GB(서빙과 공유 불가), 자가 GGUF→Ollama
  미보증, 데이터 반출 금지로 클라우드 학습 불가.
- **원인 불일치**: 실측 오답 5건(docs/22 §0) 중 "모델에 지식이 없어서"는 0건 — 전부 표 붕괴·검색·
  추론행동·산술. LLM 재고 조건: 드라이버 550+ & Ampere+ GPU & 프롬프트로 안 잡히는 순응 문제 실측 시
  소규모 형식 LoRA(LIMA류)만.

## 1. 지렛대 ① — 결정적 표 복원 (파일럿 중 VLM 불필요 판명)

**발견**: 표 병합("51"=5/1)의 근원은 HWP **셀 안의 여러 문단을 구분자 없이 이어붙인 것**
(hwp-hwpx-parser `extract_text()`·`TableData` 공통). 원본에는 구조가 온전히 있다:
- `.hwpx` = OWPML XML zip → `<hp:tc>` 셀 안 `<hp:p>` 문단 리스트를 직접 읽으면 정확한 짝 복원
  (실측: 복무규정 별표1 → `결혼 | 본인∥자녀 | 5∥1`, `사망 | 4대상 | 5∥3∥3∥3` ✅)
- `.hwp` = HWP5Reader의 `_extract_cell_text`가 문단 단위 텍스트를 보유 → 서브클래스로
  문단 구분자 보존 조인
- **VLM(Qwen2.5-VL) 경로는 불필요** — 결정적 파싱이 가능한데 생성 모델을 쓸 이유가 없음
  (무환각 원칙에도 부합). PDF 원본 가이드는 PyMuPDF `find_tables()`로 동일 접근(2차).

**구현**(`tools/01p_table_restore.py` + `tools/hwp_tables.py`):
- 입력: 01o 손상 목록(`table_integrity.json`) × 원본(`rule_files/`·`research_rule_files/`) 매칭
- 출력: **스테이징 제안** `tools/index/table_restore/<문서>.md` — 복원된 표(셀 내 줄바꿈=`<br>`) +
  출처(원본 파일·표 번호) + 기존 볼트 표와의 대비. ⛔ **볼트 자동 반영 금지** — 사람 검수 후 수동 반영.
- 향후 유입 차단: `01_hwp_to_md.py`(‧01c)의 표 렌더를 문단 보존 조인으로 패치(형식 교정 — 의역 아님).

**수용 기준**: ⓐ 실사고 2건 정답 복원(부모상 50만, 결혼 5/1·사망 5/3/3/3) ⓑ 손상 9개 문서 중
원본 확보분 전체에 제안 생성 ⓒ 복원 표가 P0-3 휴리스틱에 더 이상 손상 판정되지 않음
ⓓ 검수 반영 후 재색인하면 경조금류 질문이 유보 없이 정답(수치 게이트 통과).

## 2. 지렛대 ② — 검색기(임베딩·리랭커) 도메인 파인튜닝 실험

**근거**: 임베딩 FT는 수백~수천 쌍으로 유의미 개선(hard negative 필수), 리랭커 도메인 FT P@1 +5.19pp
사례. KURE-v1 자체가 bge-m3의 한국어 FT 산물(레시피 공개, CachedGISTEmbedLoss). 0.6B급이라
**24GB 1장 fp16 온프레미스 가능** — 유일하게 우리 하드웨어에 맞는 "가중치 레벨" 개입.

**실험 설계**(채택은 A/B 입증 시에만):
1. 학습쌍: ⓐ 골든셋 50(질문→정답 청크) ⓑ 실로그 👍 문답 ⓒ **합성 쿼리** — 로컬 Qwen3.5-9B로
   청크당 질문 1~2개 생성(InPars/GPL 방식, 온프레미스라 반출 없음). hard negative = 현 인덱스
   top-k 중 비정답.
2. 학습: sentence-transformers MNRL(또는 GIST), fp16, GPU1, 1 epoch 저LR — 산출물
   `models/kure-kei-ft/`(gitignore).
3. 평가: 테스트 인덱스 재구축(`tools/chroma.test/`) → `eval/run.sh` A/B — **strict Hit@1/@3 개선 +
   무회귀**가 채택 조건. 특히 실측 갭(문서수발 단독 질의, 직급 2-hop, tg05) 개선 여부.
4. 리랭커 FT는 임베딩 결과 확인 후 2차(재색인 불필요라 평가 쌈).

**수용 기준**: ⓐ 합성쌍 ≥500 + 품질 표본검사 ⓑ A/B 리포트(before/after 표) ⓒ 채택/보류 권고 명시.
⛔ 학습·평가 전 과정 온프레미스(데이터 반출 없음), 서빙 GPU 경합 시 학습 중단 우선.

## 3. 지렛대 ③ — 구조화 수치 스토어 (스펙만, 구현은 별도 승인)

**목표**: 별표의 (규정, 표, 구분, 항목) → 값을 SQLite에 결정적으로 저장, "숙박비 상한 얼마?"류
값 질문에 **조회 결과를 근거 블록으로 주입**(생성이 아니라 조회 — 수치 게이트의 다음 단계).
- 소스: ①의 복원된 구조화 표(셀 단위) → `01q_table_store.py`(추출) + `regs_values.sqlite`(gitignore)
- 회수 경로: 값 질문 감지 시 표 스토어 조회 → 매칭 행을 "(수치 스토어)" 라벨 블록으로 첨부 —
  LLM은 그대로 인용만. 미매칭이면 현행 그대로.
- 선행 조건: ①의 표 복원 + 사람 검수 완료분만 적재(⛔미검수 표 값 서빙 금지).
- 참고 선례: TableRAG(2025)·TAG(CIDR 2025) — 규제 도메인 hybrid symbolic+RAG.
