## 2. ⛔ 필수 갱신 매트릭스 — "이 변경이면 이 문서" (작업 마감 체크리스트)
| 변경 유형 | 필수 | 조건부 |

- **커밋 메시지에 `(docs/NN §M)` 참조를 남긴다** — 코드↔문서 양방향 추적의 최소 단위.
- 대장(요구사항) 규약은 대장 문서 상단이 정본 — 여기서 중복 정의하지 않는다.

## 3. 문서 생성 규칙
- **새 스펙 번호**: `docs/` 최댓값+1. 파일명 `NN-한글-키워드.md`(하이픈, 확장 설명은 제목에서).
- **스펙 골격**: 첫 줄 `# docs/NN — 제목` · 인용구로 날짜+지시 원문 요약 · 섹션 §번호 ·
  말미(또는 §별) **진행 기록**(날짜·구현·검증 실측치). 계획 문서는 제목에 `(계획)` 명시,
  구현되면 진행 기록으로 상태 전환(문서 새로 만들지 않고 이어 씀 — docs/50·51·52 관례).
- **후속 작업은 새 문서가 아니라 기존 스펙의 §추가**가 기본(같은 기능 = 같은 문서).
  문서를 새로 파는 기준: 다른 기능이거나, 기존 문서가 완결된 다른 국면일 때.
- **패치노트**: `changelog_lint.py`가 정본 규약(필수 필드·⛔규정 값·인프라 정보 금지·60자 요약).
  작성 즉시 린트 실행. 버그 수정은 bugreport(증상→원인→해결→개선 — 분석기 재발 대조가 소비).
- **인용 우선, 복제 금지**: 같은 사실을 두 문서에 쓰지 않는다 — 정본 한 곳 + 나머지는 링크.
  수치(청크 수 등)는 시점 명기(`2026-07-16 실측`) — 무시점 수치가 드리프트의 주범.

## 4. 드리프트 점검 (문서가 낡았는지 아는 법)
- 주기 점검(수동 또는 Claude에게 "문서 드리프트 점검" 지시):
  ⓐ `git log --since=<마지막 문서화 커밋>`에서 feat/fix/security를 §2 매트릭스와 대조
  ⓑ 패치노트 커버리지: 사용자 노출 커밋 ↔ `_changelog/` 노트 대조(2026-07-17 백필 방법론 — 대장 #20)
  ⓒ 수치 검증: README·docs의 실측치(문서 수·청크 수)를 현재 값과 대조
- 대규모 백필은 워크플로(큐레이터→작성→린트→완전성 크리틱) — 대장 #20이 선례.
