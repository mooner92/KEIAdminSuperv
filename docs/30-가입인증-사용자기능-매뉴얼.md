# 30. 가입·이메일 인증·사용자 기능 매뉴얼 (docs/29 §1·§3·§4 구현 상세)

> 무엇이 어떻게 돌아가는지의 단일 참조 문서. 스펙·경위는 `docs/29`, 코드는 `tools/app_api.py` ·
> `web/components/Login.tsx` · `web/components/AdminUsers.tsx` · `web/components/ChatApp.tsx`.

## 1. 이메일 인증 — 원리

### 1.1 전체 흐름 (3단계, 쿠키는 마지막에만)

```
[가입]  POST /app/auth/register {username=이메일, password}
          ├─ 형식·도메인 검증(@kei.re.kr) ── 실패 → 400 (계정 생성 안 함)
          ├─ User 생성: verified=False (로그인 불가 상태)
          ├─ 6자리 코드 생성 → VerifyCode 저장(해시만) → SMTP 발송
          └─ 응답 {pending:true}  ⛔ 쿠키 없음 — 인증 전엔 세션이 생기지 않는다

[인증]  POST /app/auth/verify {username, code}
          ├─ 코드 대조(HMAC 해시 비교) ── 오답 → attempts+1, 5회면 코드 무효(410)
          ├─ 성공: verified=True + VerifyCode 삭제(1회용)
          └─ 이때 비로소 JWT 쿠키 발급 = 로그인 완료

[로그인] POST /app/auth/login
          └─ 비밀번호가 맞아도 verified=False면 403 → 프론트가 코드 입력 화면으로 전환
```

핵심 설계: **"이메일 소유 증명 후에만 세션"**. register가 쿠키를 주면 인증 전 계정으로
채팅이 가능해지므로, 쿠키 발급 지점을 verify 성공으로 미뤘다.

### 1.2 코드는 왜 그냥 저장하지 않고 HMAC 해시로 저장하나

- 코드 생성: `secrets.randbelow(1_000_000)` → 6자리(암호학적 난수, `random` 아님).
- 저장: `HMAC-SHA256(서버비밀키, "이메일|코드")` **해시만** DB에 둔다. 코드 원문은 어디에도 없다.
- 왜 단순 SHA256이 아니라 HMAC인가: 6자리 코드는 경우의 수가 100만뿐이라 DB가 유출되면
  단순 해시는 1초 만에 전수 대입으로 깨진다. HMAC은 **서버 비밀키(`tools/.app_secret`,
  0600·gitignore)** 없이는 대입 자체가 불가능 → DB 유출 단독으로는 코드를 복원할 수 없다.
- 온라인 대입은 별도로 막는다: **오답 5회면 코드 무효**(410 → 재발송 필요), 재발송은 60초
  쿨다운. 5/1,000,000 = 우연히 맞힐 확률 0.0005%.

### 1.3 수명·상태 규칙 (VerifyCode 테이블)

| 필드 | 규칙 |
|---|---|
| `email` | 이메일당 **최신 1건만** — 재발송 시 이전 코드 삭제 후 새 코드 |
| `code_hash` | HMAC-SHA256 (원문 미저장) |
| `expires_at` | 발급 +10분(`CODE_TTL`). 지나면 410 |
| `attempts` | 오답 횟수. 5회(`CODE_MAX_ATTEMPTS`) 도달 시 정답을 넣어도 410 |
| `last_sent_at` | 재발송 쿨다운 60초(`RESEND_COOLDOWN`) 기준. 위반 시 429 |
| (인증 성공) | 행 삭제 — 코드는 1회용 |

- 재발송(`/auth/resend`)은 **비밀번호 확인을 요구** — 이메일만 알면 남의 메일함에 스팸을
  보낼 수 있는 문제 방지(본인 요청만 허용).
- 미인증 상태로 다시 register하면: 비밀번호 갱신 + 코드 재발송(같은 쿨다운 적용).
  이미 인증된 이메일이면 409("로그인해 주세요").

### 1.4 도메인 제한 — fail-closed

```python
SIGNUP_DOMAINS = env "APP_SIGNUP_DOMAINS" (기본 "kei.re.kr")   # 쉼표로 복수 가능
EMAIL_RE = ^[A-Za-z0-9._%+-]+@([A-Za-z0-9.-]+\.[A-Za-z]{2,})$
```
- **allowlist** 방식: 도메인이 목록에 정확히 일치해야 통과. `kei.re.kr@evil.com`(로컬파트
  위장), `kei.re.kr.evil.com`(서브도메인 위장) 모두 거부됨 — `@` 뒤 전체를 비교하기 때문.
- env를 아예 안 넣어도 기본값이 kei.re.kr — **설정 실수가 "전부 허용"이 되지 않는다**(fail-closed).
- 이메일은 `strip().lower()`로 정규화해 저장 — `Hong@KEI.re.kr`과 `hong@kei.re.kr`은 같은 계정.

### 1.5 메일 발송 경로 (SMTP)

```
SMTP_HOST     (필수 — 미설정이면 가입 자체가 503으로 막힘, fail-closed)
SMTP_PORT     기본 25
SMTP_FROM     기본 kei-admin-llm@kei.re.kr
SMTP_USER/PASS  릴레이가 인증을 요구할 때만
SMTP_STARTTLS=1 TLS 승격이 필요할 때만
```
- 표준 라이브러리 `smtplib` + `MIMEText`(UTF-8) — 외부 의존성 없음. 온프레미스라 **사내
  SMTP 릴레이**를 써야 한다(인터넷 차단 환경). ⚠ 릴레이 정보 확보가 prod 전환의 유일한 블로커.
- 발송 실패(릴레이 다운 포함) 시에도 503 — "메일 못 보내는데 가입은 열림" 상태를 만들지 않는다.
  (단, `APP_DEV_ECHO_CODE=1`인 dev에서는 발송이 실패해도 코드로 계속 진행 — 개발 편의.)
- **2026-07-13 실측(경로 차단 확인)**: `kei.re.kr`의 MX·SPF = `spam.kei.re.kr`(203.250.99.64)
  단일. 이 GPU 서버(192.168.1.104)에서 203.250.99.64/.62의 **25·587·465 전부 방화벽 차단** →
  현재 이 서버는 메일을 보낼 수 없다. **전산 담당 요청 필요**:
  「192.168.1.104 → spam.kei.re.kr(203.250.99.64):25 SMTP 릴레이 허용
  (발신 kei-admin-llm@kei.re.kr, 수신 @kei.re.kr 한정, 용도: 행정 LLM 가입 인증 코드 발송)」.
  개방 후 `deploy/ecosystem.dev-0703.config.js`의 SMTP_* 주석만 해제하면 즉시 실발송 전환.

### 1.6 개발·E2E 모드 (운영 금지)

- `APP_DEV_ECHO_CODE=1`이면 **코드를 register/resend 응답에 동봉**(`dev_code`).
  프론트는 이를 감지해 "개발 모드 — 인증 코드: NNNNNN" 안내문으로 표시.
- echo와 SMTP는 **공존 가능**: `SMTP_HOST`가 설정돼 있으면 echo 모드에서도 실제 발송을
  시도한다(응답 `sent: true/false`) — dev에서 실메일 검증과 E2E(코드 자동 취득)를 동시에 유지.
- dev PM2(`deploy/ecosystem.dev-0703.config.js`)에만 설정돼 있다. ⛔ **prod 환경변수에 절대
  넣지 말 것** — 넣는 순간 인증이 무의미해진다(코드가 응답으로 노출).

### 1.7 기존 계정 마이그레이션 (잠금 없음)

- `user` 테이블에 `verified` 컬럼이 없으면 기동 시 1회:
  `ALTER TABLE user ADD COLUMN verified ... DEFAULT 0` → **기존 행 전부 `UPDATE verified=1`**.
- 즉 정책 이전 가입자(admintest, 21963 등 레거시 아이디)는 "인증됨"으로 백필되어 로그인
  유지. 이후 신규 가입만 이메일 정책을 탄다. (SQLModel `create_all`은 기존 테이블에 컬럼을
  추가하지 않아 수동 마이그레이션이 필요했음 — `_migrate_user_verified()`.)

### 1.8 세션(기존 구조 그대로 — 참고)

- 인증 성공 시 JWT(`{uid, exp}`, HS256, 서명키=`.app_secret`) 발급 → `kei_session` 쿠키
  (**HttpOnly**·SameSite=Lax·14일). HttpOnly라 JS에서 토큰 접근 불가(XSS 내성).
- 내부망 HTTP라 `secure=False` — Cloudflare ZT/HTTPS 전환 시 `secure=True` 권장(기존 주석).
- 로그인 무차별 대입은 기존 레이트리밋(사용자+IP 8회/5분 → 429)이 그대로 방어.

### 1.9 프론트 흐름 (Login.tsx — 3모드 상태기계)

```
login ──(계정 없음)──▶ register ──(코드 발송됨)──▶ verify ──(성공)──▶ onAuthed
  └──(403 미인증 계정)────────────────────────────▶ verify (재발송 버튼 제공)
```
- 코드 입력은 숫자만·6자리 제한, 6자리가 되어야 버튼 활성.
- 미인증 계정이 로그인을 시도하면 403을 감지해 자동으로 verify 단계로 보낸다(막다른 길 없음).

## 2. 관리자 사용자 목록 (§4)

- `GET /app/users` — `current_admin` 의존성(= `APP_ADMINS` 목록 기반, **미설정이면 아무도
  관리자 아님** fail-closed, 기존 규칙 그대로).
- 반환: `username(=이메일)·created_at·verified·is_admin·chats(채팅 세션 수)·last_active
  (세션 updated_at 최댓값)`. **여기까지가 전부다** — 질문·답변 본문을 반환하는 필드가 없고,
  타인 채팅을 읽는 엔드포인트는 이번에도 추가하지 않았다(P2.5 프라이버시 원칙 ⓐ 불변).
- UI: `/admin` 👥 사용자 탭(flag `user_directory`) — 표 상단에 "채팅 내용은 관리자도 볼 수
  없습니다" 고지 문구를 상시 표시.

## 3. 인기 검색 키워드 (§1)

### 3.1 집계 원리 — 무LLM·결정적

1. **사전(lexicon)**: 여정 트리거 키워드(`rag_core._ensure_journey_triggers`) + 용어집
   `tools/index/defterms.json` 용어명(2~12자). 일반어 스톱워드(`신청`·`확인`·`휴가류 아님` 등
   실측 노이즈) 제외. 기동 후 1회 로드·캐시.
2. **매칭**: 기간 내 사용자 질문(Message, role=user)마다 사전을 **길이 내림차순**으로 스캔 —
   `연차휴가`가 잡히면 그 부분 문자열 `휴가`는 세지 않는다(최장 일치 우선, 이중 집계 방지).
3. **k-익명 게이트**: 키워드별로 (서로 다른 사용자 집합, 질문 수)를 세고, **서로 다른 사용자
   `STATS_MIN_USERS`(기본 3)명 미만인 키워드는 응답에서 제외**. 1~2명만 물은 고유·민감
   질문이 키워드로도 새지 않게 하는 장치(P2.5 대시보드와 같은 상수).
4. 상위 10개만, 5분 인메모리 캐시(`days`별). 질문 본문은 어떤 형태로도 반환하지 않는다.

### 3.2 노출

- `GET /app/trending?days=1|7|30`(로그인 사용자 누구나 — 반환이 익명 집계뿐이라 안전).
- 채팅 빈 화면 "📈 요즘 많이 찾는 키워드" 칩(flag `trending_keywords`).
  클릭은 **입력창 프리필만** — 자동 전송 없음(원문 선택 질문과 동일한 오발사 방지 원칙).
