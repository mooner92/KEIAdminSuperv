# 56 — 오류 수집·관측 고도화 계획 (Sentry 개념의 온프레미스 이식)

> [!note] 결정(2026-07-21): **P0만 구현, 나머지는 조건부 보류.** "꼭 필요한가" 재검토 결과
> P2~P4(프론트 수집·이슈 탭·지문 그룹핑·릴리스·성능)는 내부 수십 명·prod 미배포 규모엔 과함(YAGNI)으로
> 판단. **P0("죽으면 안다")만** 진행 — 기존 keep-alive 스레드에 헬스체크 + 미처리 예외 알림,
> 둘 다 기존 MaintNotice 재사용(새 테이블·탭 0). 구현·검증 완료는 아래 §8.

> 2026-07-21 계획(구현 전). 사용자 지시: "sentry.io 참고해서 로그 수집·통계 부분 개선 계획".
> 결론 요약: **Sentry SaaS는 불가(절대 규칙 5), self-host Sentry는 과체급** → PostHog 때와 같은
> 판단으로 **Sentry의 핵심 개념 6가지를 기존 스택(SQLite+FastAPI+admin 탭+MaintNotice)에 이식**한다.
> 우리만의 차별점: 잡힌 오류를 기존 **제보→게이트 분석→오토픽스** 루프에 직결할 수 있다(Sentry엔 없음).

## 0. 동기 — 오늘 실제로 겪은 구멍

2026-07-21, 재색인 후 dev API가 옛 Chroma 컬렉션 핸들을 물고 **채팅이 전부 500**이었다.
PM2 로그에는 트레이스백이 쌓이고 있었지만 **아무도 몰랐고**, 사용자가 눌러보고서야 발견했다.
Sentry가 있었다면: 첫 500 발생 즉시 이슈 생성 → 알림 → (우리 스택에선) 오토픽스 제보까지 자동.

## 1. 현황 (2026-07-21 실측)

| 영역 | 현재 | 구멍 |
|---|---|---|
| 사용량 | `track()` 이벤트명만(페이로드 금지) → UsageEvent → /app/stats(k-anon) → 📈통계 탭 | 양호 — 이번 계획 범위 아님 |
| 프론트 오류 | ErrorBoundary가 `console.error`만 | **서버로 안 감. 발생 사실 자체를 모름** |
| 백엔드 오류 | uvicorn 500 트레이스백 → PM2 로그 파일 | **알림 없음. 사람이 로그 열어야 발견** |
| 헬스체크 | 없음(수동 curl) | 오늘 같은 "죽어 있는데 모름" 재발 가능 |
| 릴리스 태깅 | BUILD_ID(footer v.dev) 존재 | 오류와 연결 안 됨 — "어느 배포부터 깨졌나" 못 물음 |
| 성능 | 없음(체감뿐) | RAG 응답 지연 악화를 수치로 못 잡음 |

## 2. 왜 Sentry(제품)를 안 쓰나

- **SaaS**: 오류 페이로드(스택·URL·질문 흔적)가 외부로 나간다 — ⛔절대 규칙 5 위반. 즉시 탈락.
- **Self-host Sentry**: Kafka·ClickHouse·Redis 등 컨테이너 20+, RAM 16GB+ 권장. 사용자 수십 명
  내부 도구에 과체급이고 GPU 서버 자원과 경합. PostHog 결론("가능하나 부적합")과 동일.
- **GlitchTip**(Sentry 호환 경량 대안, Django+Postgres 2컨테이너): 후보로는 성립하나,
  ⓐ 별도 DB·컨테이너 운영 부담 ⓑ 기존 관리자 탭·MaintNotice·오토픽스 루프와 이중화
  ⓒ 우리 규모(이벤트/일 수백)에 자체 구현으로 충분. → **자체 구현 우선, GlitchTip은 §7 재평가 조건부**.

## 3. 이식할 Sentry 핵심 개념 → 우리 구현

| Sentry 개념 | 뜻 | 우리 구현 |
|---|---|---|
| **Error Event** | 예외 1건(스택·컨텍스트) | `ErrorEvent` 테이블(SQLite) — 프론트 window.onerror/unhandledrejection/ErrorBoundary + 백엔드 FastAPI 예외 미들웨어 |
| **Issue(그룹핑)** | 같은 원인의 이벤트 묶음(지문) | `fingerprint = hash(type + 정규화된 message + top frame)` — 건수·first/last_seen·상태(미해결/해결/무시) |
| **Release** | 배포 버전별 추적 | 기존 BUILD_ID(프론트)·git short hash(백엔드)를 이벤트에 태깅 → "release X부터 발생/재발(regression)" |
| **Breadcrumbs** | 오류 직전 행동 궤적 | 프론트 최근 행동 링버퍼(라우트 이동·클릭한 기능·API 상태코드) 20개 — ⛔질문 본문·입력값 제외 |
| **Alerts** | 새 이슈·급증 알림 | 기존 **MaintNotice + 🔔배지 + 브라우저 알림** 재사용. 규칙: 신규 이슈 / 해결됐던 이슈 재발 / 분당 N건 급증 |
| **Performance(Tx)** | 구간별 지연 | RAG 경로 스팬 계측: retrieve(밀집/리랭크)·generate(첫토큰/전체)·전체 — p50/p95를 통계 탭에 |

**우리만의 +1 (Sentry에 없는 것)**: 이슈 → 한 번의 클릭으로 **Report(버그신고) 생성 → 게이트
분석 → 🤖오토픽스**. 오류 수집이 기존 자기개선 루프의 입력이 된다.

## 4. 단계별 계획

### P1 — 오류 수집 MVP (효과 최대, 1~2일)
- 프론트 `lib/errlog.ts`: `window.onerror`·`unhandledrejection`·ErrorBoundary 훅 → `POST /app/errors`
  (배치 전송·중복 디바운스·릴리스=BUILD_ID·라우트 패턴만). **개인정보 0 원칙**: 질문/입력값/스니펫
  미포함, 스택 4KB 절단, URL은 라우트 패턴(pathname)만.
- 백엔드: FastAPI 예외 미들웨어 → 동일 테이블(`side=server`, 트레이스백 절단, 라우트·상태코드).
- 지문 그룹핑 + `Issue` 뷰(집계 쿼리로 시작, 테이블 분리는 나중).
- **헬스체크(dead man's switch)**: 기존 분석기 cron에 1분 셀프 핑(`/v1 200?` + chroma 컬렉션 헬스)
  → 실패 시 MaintNotice. 오늘 사고 직접 재발 방지.

### P2 — 이슈 관리 + 알림 (1일)
- `/admin` **🐞 오류** 탭(AdminErrors 컴포넌트, Section+PagedList 관례): 이슈 목록(건수·추세
  스파크라인·release·최근 발생), 상태 토글(미해결/해결/무시), 이벤트 상세(스택·breadcrumbs).
- 알림 규칙 3종(신규/재발/급증) → MaintNotice(kind=error) + 🔔 + 브라우저 알림.
- **오토픽스 연결**: 이슈 카드에 [🤖 제보로 전환] — Report 생성(유형=버그신고, 본문=지문·스택 요약).

### P3 — 릴리스·성능 (1일)
- 릴리스 비교: 이슈별 "first_seen release" / 해결 후 재발 감지(regression 배지).
- RAG 스팬 계측(`rag_core`에 타이밍 이미 일부 존재 여부 확인 후): retrieve·rerank·generate
  p50/p95/실패율 → 통계 탭에 카드 추가. 임계 초과 시 경고 알림.

### P4 — 조건부 확장 (보류)
- 세션 리플레이 대체: breadcrumbs 타임라인 뷰로 충분한지 P2 운영 후 판단.
- GlitchTip 재평가 조건: ⓐ이벤트가 일 1만+ ⓑSQLite 집계가 느려짐 ⓒ다중 서비스 확장. 그 전엔 안 함.

## 5. 프라이버시·가드레일 (P2.5 원칙 승계)

- 오류 페이로드에 **질문·답변·입력값·규정 스니펫 절대 미포함**(코드 리뷰 체크리스트에 명시).
- breadcrumbs는 행동 이름·라우트 패턴만(기존 track 이벤트명 allowlist 재사용).
- 관리자만 열람(current_admin), 통계 탭 노출은 집계만.
- 기능 플래그 `error_tracking`(release 관례 off→dev 검증→on) + 수집량 상한(분당/일당 캡, 초과 시 드롭 카운트만).

## 6. 하지 않기로 한 것

- Sentry/GlitchTip/PostHog 도입(§2) · 외부 전송 일절 · 소스맵 업로드 인프라(스택은 압축본 기준
  + 릴리스로 좁힘 — 필요해지면 P4에서 재검토) · 세션 리플레이(과함).

## 7. 성공 기준

- 오늘 같은 "500인데 모름"이 **알림 도달 시간 < 5분**으로.
- 프론트 백지/렌더 오류가 관리자 탭에 지문 단위로 보임.
- 배포 후 회귀를 release 비교로 30초 안에 특정.
- 오류 → 오토픽스 제보 전환이 클릭 1회.
