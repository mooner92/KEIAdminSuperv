# 69 — 답변 게이트 정비: 과밀 진단과 개선계획 (2026-08-10)

> 운영자 질문: "게이트가 너무 많고 촘촘한데 오히려 역효과를 일으키고 있진 않은지,
> T 계획들과 충돌나진 않는지 판단해서 개선계획 작성."
> 근거: `rag_core.py` 전수 + 최근 6회차 답변 2,496건 실측 + 코드 감사 2건(T1·T2~T4 충돌 감사).
> 관련: docs/22(신뢰 게이트 명세) · docs/26(인용 배지 보류 결정) · docs/68(T 계획 — §5의 순서를 본 문서가 대체).

## 0. 한 줄 결론

**"게이트가 많아서 답변이 나빠진다"는 실측상 근거가 약하다. 진짜 문제는 셋이다:**
① 게이트가 **얼마나 발동하는지 잴 데이터가 없고**(계측 절삭),
② 게이트끼리 · 게이트↔평가계가 **검증 안 된 상호작용**을 갖고 있으며(거부판정 오염이 대표),
③ 게이트 **신설 비용이 선형으로 증가**한다(신설 1건당 갱신 지점 ~10곳, 이번 주 실사고 2회).

→ 프루닝(끄기)이 아니라 **계측 → 상호작용 수리 → 예산 명시화 → 데이터 기반 정리** 순서.

## 2. 실측 — "역효과" 가설 검증

최근 6회차 **답변 2,496건** 전수 스캔:

| 지표 | 값 | 해석 |
|---|---|---|
| 답변 내 ⚠️ 경고 존재 | **1.8%** (46건) | 노트가 답변을 어지럽힌다는 우려는 **현재로선 낮음** |
| 수치 게이트 발동 | 1.3% | 〃 |
| 개수 한정 노트 | 2.4% | 〃 |
| 근거 수 평균 / 최대 | **6.9 / 8** | 기본 5 + 자동첨부 평균 ~1.9개 — 첨부는 실제로 많이 일어남 |
| 라우트별 발동률 | **측정 불가** | ⛔ `daily_answer.py:50`이 저장 시 근거를 3키로 절삭 — 플래그 소실 |
| 컨텍스트 절단율 | **측정 불가** | 〃 (`절단` 플래그도 소실) |

**정직한 결론**: "과밀해서 역효과"라는 가설은 **판정할 데이터가 없다.**
경고 노트는 드물게 발동하지만, 자동첨부(층1 라우트 9종)는 답변마다 평균 ~2개씩 실제로
동작하는데 **무엇이 언제 발동하는지, 그 때문에 절단이 얼마나 나는지 아무도 모른다.**
게이트를 늘릴수록 이 블라인드 스팟만 커진다.

## 3. 확인된 역효과 (전부 file:line 근거)

### 🔴 R1. 게이트 노트가 거부 판정을 오염시킨다 — 실증됨, 최우선 수리

`refusal_detect._head`(35~45행)는 첫 문단이 40자 미만이면 앞 200자를 스캔하는데,
노트는 `\n\n` 뒤에 붙으므로 **짧은 답변에서는 노트가 스캔 범위에 들어온다.**
`numeric_guard_note` 문구에 이미 `확인되지 않았습니다`가 있고 이는 `REFUSAL_RE`(`확인되지\s*않`)와
매치 → **정상 답변이 거부로 채점**될 수 있다. 소비처 5곳(일일 채점·`/app/stats` 거부율 등).
게이트가 늘수록(T1 포함) 이 오염이 **증폭**된다 — T9(거부 오탐) 사고와 같은 계열.

### 🔴 R2. 계측 절삭 — 게이트 운영의 눈이 없다

`daily_answer.py:50`: `{k: s.get(k) for k in ("규정명","조","snippet")}` — defterm_route·
impact_route·amount_route·scope_anchor·`절단` 등 **15종 플래그가 저장 전에 버려진다.**
docs/26이 "무음 텔레메트리"를 결정해 놓고도, 텔레메트리를 만들 원료가 소실되는 구조.

### 🟠 R3. 맨앞 삽입 경쟁 — 우선순위가 코드 순서로 암묵 결정

defterm(1580) · amount(1609) · impact(1639) 모두 `srcs.insert(0, …)`. 동시 발동 시
**나중에 실행된 라우트가 최전방**을 차지한다(현재: impact > amount > defterm). 이 순서는
누구도 설계하지 않았다. SYSTEM 규칙 4("핵심 조문 맨 앞")와 기계 삽입이 경합한다.

### 🟠 R4. 예산 경쟁이 평가 통계를 오염시킬 수 있다 — T0·T2 직결

기본 5 + 별표≤3 + 준용≤2 + scope≤2 + 라우트들 vs **예산 6000자**. 초과 시 `_cap_blocks`가
꼬리를 자르고 srcs에서도 뺀다(동기화 자체는 올바름 — T1 감사에서 불변식 검증).
**그러나** 절단으로 기대 근거가 탈락하면 평가의 `retrieved_expected()`가 이를
**'검색실패'로 오분류**한다 — 검색은 찾았는데 예산이 밀어낸 것. 절단율을 못 재니(R2)
이 오염의 규모도 모른다.

### 🟠 R5. 신설 비용 선형 증가 — 이번 주 실사고 2회

게이트/분류 1건 신설 시 갱신 지점 ~10곳(생성·화이트리스트·버킷·행동후보·라벨맵·캡션·
문서·MLflow·회귀×2). `근거부적합` 유실(08-07)과 거부형 91건 유실(구조 결함)이 모두
이 비용을 안 치러서 생겼다. **회귀가 지키는 건 그중 2곳뿐.**

### 🟡 R6. 기타
- **이중 구성 경로**: env(RAG_*) > DB플래그 > 기본값의 3단 우선순위가 라우트마다 달라
  현재 상태의 단일 뷰가 없다.
- **평가 비대칭**: `run_eval.py`는 `rag_core.answer()` 직접 호출(노트 없음), 일일 평가는
  API 경유(노트 있음) — 같은 모델·다른 텍스트를 채점.
- **면책 최후행 깨짐**: 노트가 `_ensure_disclaimer` **뒤에** 붙어 면책이 마지막 줄이 아니게 됨.

## 4. T 계획과의 충돌 지도

| | 충돌 | 내용 |

| **T0**(거부형 91건) | R1·R4 | 거부 오염이 낀 채 재집계하면 또 틀린 숫자 — R1 수리와 **동시에** |
| **T1**(출처 가드) | R1·R2·R3 | 노트 1개 추가 = R1 증폭. docs/26은 배지 보류 결정. **텔레메트리(R2 수리) 선행이면 docs/26의 (다)안과 정확히 합치** |

## 5. 개선계획

### P0 — 계측 복원 (역효과 판정의 전제, ~반나절) ⭐

1. `daily_answer.py` 절삭 키에 라우트 플래그 15종 + `절단` 추가(또는 요약 필드 `x_gates`).
2. `/v1`·`/app` 응답에는 이미 실려 있으므로 **저장만 고치면 됨** — 서비스 무변경.
3. 관리자 대시보드에 일별 게이트 발동 집계(무음 텔레메트리 — **docs/26 결정 그대로 구현**).
4. **7일 수집 후** 라우트별 발동률·절단율·절단 유발 '가짜 검색실패' 규모를 수치로 확보.

### P1 — 상호작용 수리 (실증된 결함, T0와 같은 주에)

1. **거부 오염(R1)**: `refusal_detect._head`가 노트 마커(⚠️/ℹ️) 이후를 스캔하지 않게 —
   정본 한 곳 수정으로 소비처 5곳 동시 해결. + "모든 노트 문구는 REFUSAL_RE 비트리거"를
   소스 검사 회귀로 고정(신설 노트가 자동으로 규약을 따르게).
2. **면책 최후행**: `post_answer_notes`를 면책 **앞**에 삽입하도록 순서 교정.
3. **T0 재집계**: 1과 같은 커밋 열차에서 — 오염 제거 후의 숫자가 진짜 기준선.

### P2 — 예산·우선순위 명시화 (P0 데이터 확보 후)

1. 맨앞 삽입 경쟁(R3) → **명시적 우선순위 상수** 하나로(`ROUTE_PRIORITY = (…)`).
2. 자동첨부 **총량 상한**(예: 기본 5 + 첨부 ≤3) + 절단 시 어느 라우트가 밀렸는지 로그.
3. 평가의 `retrieved_expected()`가 `절단` 탈락을 검색실패로 세지 않게(별도 원인 `예산절단`) —
   ⚠ R5 규약대로 **생성→집계→표시 전 경로 + 버킷 등록을 같은 커밋에서**.

### P3 — 데이터 기반 정리 (P0 + 7일 후)

1. 발동률 ~0 또는 이득 미측정 라우트 → 기본 off (선례: SECTION_DIVERSITY·HYBRID).
   후보는 지금 지목하지 않는다 — **데이터가 지목하게 한다.**
2. **게이트 신설 체크리스트**를 CLAUDE.md 규약으로: 계측 필드 + REFUSAL_RE-safe 문구 +
   전 경로 회귀 + 버킷 등록 + 문서. R5의 선형 비용을 규약으로 상수화.
3. 이중 구성 경로(R6): 신규 게이트는 DB플래그 단일 경로로, env는 비상용만.

### 순서와 T 계획 통합

```
P0(계측) ──┐
P1(수리+T0) ─┴─ 같은 주
   ↓ 7일 수집
P2(예산 명시화) + T1(텔레메트리형 — docs/26 (다)안)
   ↓
P3(정리) + T2(분리 집계 — 이제 규모가 정확) + T4
```

docs/68 §4의 권고 순서(T2→T1→T4→T3)는 **본 문서로 대체**한다 — 그 순서는 계측 부재와
거부 오염을 모르던 시점의 판단이다.

## 6. 하지 않을 것

- **일괄 프루닝** — 발동률도 모르면서 끄는 것은 켜는 것만큼 근거가 없다. ARTICLE_STATUS·
  TABLE_GUARD처럼 절대규칙 방어선인 게이트는 발동률과 무관하게 유지.
- **게이트 통합 대수술** — 층4의 노트 이음매(`post_answer_notes`)는 이미 올바른 단일
  구조다(스트림+비스트림 공용). 구조가 아니라 계측과 문구가 문제다.
- **CTX 예산 증액으로 회피** — 8K 모델에서 6000자는 실측 산출값(100문항 감사). 예산을
  늘리는 게 아니라 첨부 우선순위를 명시하는 것이 맞다.

## 7. 열어둔 질문

- 자동첨부 평균 ~2개/답변이 **답변 품질에 기여하는지** — P0 계측 후 라우트별로
  "첨부가 실제로 인용됐는가"를 추적해야 답할 수 있다.
- 층2(SYSTEM 16규칙)의 밀도는 이번 범위 밖 — 규칙 간 충돌 여부는 별도 감사가 필요하다.
