# FeedbackPlan — 제보 분석 계획 생성

**감지**: `feedback_analyze` — 사용자 제보를 읽고 **계획을 만들었을 때만**(계획 없음은 `run_log`에만 남는다).
**⛔ 쓰기 경로 없음** — 이 분석기는 볼트·검수상태를 바꾸지 않는다. 계획은 제안이다.

## 1. 계획을 읽는다
`/admin` 의견함 → 해당 제보 → 게이트 보고서. 또는 `tools/index/feedback_plans/plan_*.md`.

보고서엔 게이트 0~3 분류·원인분석·Claude Code 프롬프트·확인포인트가 있다.

## 2. 게이트로 판단
| 게이트 | 뜻 | 대응 |
|---|---|---|
| 0 | 재현 안 됨 / 이미 고쳐짐 | 닫는다 |
| 1 | 콘텐츠 문제(원문 오류·누락) | 검수 큐로 — ⛔검수상태는 **사람만** 바꾼다 |
| 2 | 코드 문제, 범위 명확 | 오토픽스 🤖 또는 직접 수정 |
| 3 | 설계 문제 | docs에 기록하고 계획 세운다 |

## 3. 원문 오류 주장은 검수가 답이 아니다
"틀린 정보가 들어갔다"는 제보에 검수상태를 먼저 의심하지 않는다 — 원문은 kordoc으로 추출해 변환 오류가 거의 없다.
**검색·청킹·프롬프트 쪽을 먼저 본다.**

## 4. 계획을 안 따를 수도 있다
LLM이 만든 계획이다. 원인분석이 틀렸으면 무시하고 직접 진단한다 — 계획의 존재가 정확성을 보증하지 않는다.
