## 2. ⚠ F1 (HIGH) — 1차 조치가 불완전했다

**가장 중요한 결과이고, 원인은 내 수정이다.**

1차에서 F17(관리자 선점)을 고칠 때 `register`의 부트스트랩만 `_has_verified_admin`으로
막고, **`login`의 예외는 그대로 뒀다.**

```python
# tools/app_api.py:959
if ok and not u.verified and not _is_admin_name(u.username):
```

`APP_ADMINS`에 있는 이름이면 `verified` 검사를 통째로 면제한다. 그래서 공격은
한 단계 늘었을 뿐 여전히 성립한다:

1. 미가입 `APP_ADMINS` 주소로 가입 → 1차 조치대로 즉시 관리자는 **안 된다**(verified=False 행만 생성)
2. **같은 자격으로 로그인** → 959행이 verified 검사를 면제 → 964행 `is_admin`=True → 관리자 쿠키 발급

### 더 나쁜 것 — 회귀 테스트가 통과한다

`tools/test_auth_hardening.py::t_f17_관리자_존재시_선점_불가`는 **register 응답만 검사**하고
로그인을 시도하지 않는다. 구멍이 열려 있는데 초록불이 뜬다.

이건 내가 같은 세션에서 `verify-changelog`를 두고 지적했던 **'공허한 통과'**와 정확히 같은
실패다(`docs/63 §12`). 지적한 사람이 같은 실수를 했다.

### 현재 악용 가능성

**prod는 지금 악용 불가**다 — `APP_ADMINS`가 `21963`이고 `valid_signup_email`(@kei.re.kr)을
통과하지 못해 가입 자체가 안 된다. 다만 **운영자가 실제 이메일 주소를 명단에 추가하고
그 사람이 가입하기 전** 구간에서 즉시 악용 가능해진다.

### 조치

로그인 게이트에서 `_is_admin_name` 예외를 제거하고 `verified`를 예외 없이 요구한다.
데드락 방지는 이미 `register`에 `not _has_verified_admin(s)`로 올바르게 있다.
**회귀 테스트에 로그인 시도를 추가**해야 같은 구멍이 다시 안 생긴다(403·is_admin False 단정).

## 3. F5 — 수용했던 결정이 새 정보와 함께 재보고됨

`web/v-*.png` 스크린샷 16개. **2026-07-29 이력 정리 때 운영자 판단으로 보존**했던 항목이다
(`docs/63 §10` — 결재 권한 구조는 공개 무방).

스캔이 재보고하며 **그때 없던 정보**를 붙였다:

> 이미지가 **보안·감사 규정 목록까지** 열거한다 — 보안관리규정 · 정보보안 기본지침 ·
> 내부감사규정 · 연구과제보안관리지침.

결재 매트릭스 공개와 **"어떤 보안·감사 규정이 존재하는가"의 공개는 다른 종류의 노출**이다.
전자는 조직 운영 구조, 후자는 공격자에게 유용한 정찰 정보에 가깝다.

⛔ 이전 결정을 뒤집으라는 뜻이 아니라, **새 정보로 다시 판단할 값어치가 있다**는 뜻이다.
결정이 유지되면 그대로 두되, 이 문서에 근거가 남는다.

또 이 경로가 **가드를 우회하는 이유**는 1차에서 이미 기록했다 — 가드는 전부 **경로**를 보는데
PNG는 목록에 없다. 볼트 md는 막고 그 md를 렌더한 이미지는 통과한다.

## 4. F7 — 파일을 잠갔는데 디렉터리가 열려 있었다

**실측 확인됨**(추론 아님):

```
drwx---rwx   /KEIAdminSuperv/tools        ← 타인 쓰기 가능
drwxrwxr-x   /home/mhchoi/kei-dev-0703/tools
drwxr-xr-x   /KEIAdminSuperv
```

1차에서 `.app_secret`·`app.db`를 0600으로 잠갔지만, **파일 교체는 파일 권한이 아니라
디렉터리 권한이 정한다.** 생성·이름변경·삭제는 상위 디렉터리 권한 소관이라,
로컬 사용자가 `.app_secret`을 밀어내고 자기 키를 놓을 수 있다 → 재기동 시 그 키로
서명 검증 → 관리자 쿠키 위조.

**조치**: `chmod 750 /KEIAdminSuperv/tools`. 배포 트리 전체의 other-writable 디렉터리도 점검.

> 교훈: **파일 모드 하드닝은 디렉터리 모드 점검과 짝**이어야 한다. 둘은 다른 동작을 지킨다.
> 1차 §11에서 "원본은 막고 사본이 샌다"를 세 번 겪었는데, 이번은 "파일은 막고 경로가 샌다"였다.

## 8. 이번에 배운 것

**⑴ 부분 수정은 수정이 아니다.**
F1은 문의 절반만 잠근 결과였다. 같은 취약점의 **모든 진입 경로**를 세지 않으면
"고쳤다"는 기록만 남고 구멍은 그대로다.

**⑵ 회귀 테스트는 공격 경로 전체를 재현해야 한다.**
register만 검사한 테스트가 통과하며 login 구멍을 가렸다. 테스트가 **막았다고 주장하는 것**과
**실제로 시도하는 것**이 다르면 그건 거짓 안심이다. (`docs/63 §12`에서 남의 테스트를 두고
지적한 문제를 내 테스트가 그대로 반복했다.)

**⑶ 하드닝은 한 층만 보면 새어나간다.**
1차: 원본은 막고 사본이 샜다(3회). 2차: 파일은 막고 디렉터리가 샜다.
**보호 대상이 아니라 "어떤 동작을 막는가"로 확인**해야 한다.

**⑷ 수용한 위험도 재평가 트리거가 필요하다.**
F5는 결정이 틀렸다는 게 아니라 **판단 근거가 갱신됐다**는 사례다.
수용 결정에는 "무엇을 알고 수용했는지"가 함께 남아야 다시 판단할 수 있다.
