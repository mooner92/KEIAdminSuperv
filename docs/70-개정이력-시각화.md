# 70 — 개정 이력 시각화: "무엇이 어떻게 바뀌었나"를 보여주기

> 2026-08-12 · 운영자: "'최근 개정된 규정' 이거 같은 경우에, 어떻게 변한건지, VS Code에서
> git history 보는 것처럼 시각화해서 보여줄 수 있으면 좋겠다. 아이디어 정리하고 개선 방향 작성."
> 관련: `web/pages/now.tsx:161`(현재 카드) · docs/18(조문 정제 Track A) · specs/15(개정 반영) ·
> docs/28(취소선 개정 이력 규약).

## 0. 결론 먼저 — 반은 지금 되고, 반은 데이터가 없다

"VS Code git history처럼"의 전제는 **과거 버전이 저장돼 있다**는 것이다. 그런데:

> ⛔ **볼트는 git에 없다**(`.gitignore:11` — 내부 규정이라 공개 레포에서 분리).
> 즉 **2026-08-05 이전의 규정 원문은 이 시스템 어디에도 남아 있지 않다.**

따라서 정직한 답은 이렇게 갈린다:

| | 지금 할 수 있나 | 근거 데이터 |
|---|---|---|
| **언제 · 어느 조가** 개정됐나 (타임라인) | ✅ **가능** | `article_status.json` — 437/1,943 조문에 개정 마커 |
| **무엇이 → 무엇으로** 바뀌었나 (diff) | ⚠ **앞으로만** | `_backup/`(현재 3개) + `corpus_replace_log.jsonl`(4줄) — **개정 반영 기능을 쓴 것만** |
| 과거 개정의 원문 diff | ❌ **불가** | 원본이 존재하지 않음 |

**핵심 판단**: "과거를 복원"하려 애쓰지 말고, **오늘부터 쌓이게** 만들고 과거는 **가진 만큼만
정직하게** 보여준다. 지금 3건뿐인 백업이 1년 뒤엔 수십 건이 된다.

## 1. 지금 있는 재료 (실측)

### ⓐ `article_status.json` — 조문별 개정 **시계열** (가장 넓은 커버리지)
```
"위임전결규정#제1조": { "최근개정일": "2024.12.30", "개정횟수": 1, "개정이력": ["2024.12.30"],
                        "status": "유효", "삭제일": "", "신설": false }
```
- 1,943 조문 중 **437개에 개정 마커**, 그중 **159개는 2회 이상**.
- 연도 분포: 2021 23 · 2022 21 · 2023 120 · 2024 55 · 2025 46 · 2026 7.
- 출처는 원문에 박힌 `<개정 …>` 표기 → **텍스트는 없고 날짜만** 있다.

### ⓑ `_backup/` + `corpus_replace_log.jsonl` — 진짜 **diff의 씨앗**
- 백업: `2300_위임전결규정-<날짜>-<시각>.md` 3개 — **반영 직전 전문 스냅샷**.
- 로그: `{ts, event, target, mode, line, before, after, backup, 시행일, actor}`.
  → **줄 번호까지 아는 정확한 변경 기록**. VS Code diff에 가장 가까운 재료.
- ⚠ `before/after`는 200자 절단 저장 — 표시용으론 충분하나 **복원 정본은 백업 파일**.

### ⓒ 현재 카드 (`now.tsx:161`)
프론트매터 `개정일` 하나만 쓴다. 클릭하면 문서로 갈 뿐 "무엇이 바뀌었는지"는 어디에도 없다.

### ⓓ docs/28 취소선 규약 (놓치기 쉬운 자산)
`~~옛값~~ 현행값<!--outdated …-->` — **한 줄 안에 before/after가 공존**한다.
검색은 `strip_outdated`로 최신값만 보고, 웹 뷰어는 취소선을 렌더한다. 이미 문서 안에 있는
**미니 diff**이므로 시각화가 곧바로 활용할 수 있다.

## 2. 설계 — 3층으로 나눈다

### L1. 개정 타임라인 (지금 바로, 데이터 있음) ⭐

카드를 목록에서 **타임라인**으로 바꾼다. VS Code의 파일 히스토리 사이드바에 해당.

```
📜 위임전결규정                                        [문서 열기]
 ●─ 2026.08.03  부칙 신설 · 조문 1곳 변경 · 별표 1곳    [무엇이 바뀌었나 ▾]   ← 반영 로그 있음
 │
 ○─ 2024.12.30  제1조 외 3개 조 개정                                        ← 마커만(내용 없음)
 ○─ 2023.05.11  제12조 개정
```
- **채운 점(●)** = 우리 파이프라인이 기록한 변경(diff 열람 가능)
- **빈 점(○)** = 원문 마커만 있는 과거 개정 — **"이 시점 원문은 보관돼 있지 않습니다"** 명시
- 데이터: `article_status.json` 집계 + 로그 병합. **신규 인덱스 불필요**.
- ⚠ 정직성: 빈 점을 채운 점처럼 보이게 하면 안 된다 — 없는 것을 있는 척하는 순간 신뢰가 깨진다.

### L2. 변경 상세 diff (앞으로 쌓임)

`[무엇이 바뀌었나 ▾]`를 열면 **줄 단위 before/after**(개정 반영 패널의 `−/+` 표기 재사용):

```
제2조 공통사항                         649줄
 − (개정 전 문구)
 + (개정 후 문구)
 + (신설 항)                           651줄 뒤
별표 · 기획·행정                        356줄
 − (구 명칭) → + (신 명칭)
```
- 소스: 로그의 `before/after/mode/line` — **LLM 0회, 기록을 그대로 표시**.
- 200자 초과 변경은 "전문 보기"로 백업 ↔ 현재 파일 `difflib`(서버).
- 시각 언어를 개정 반영 패널과 **한 벌로** 유지(사용자가 두 번 배우지 않게).

### L3. 문서 내 인라인 표시 (이미 절반 구현됨)

문서 드로어에서 **바뀐 줄에 변경 마커**(VS Code gutter 상당). docs/28 취소선이 이미
렌더되므로, 로그 기반 하이라이트를 얹으면 "이 조문이 최근 개정됐다"가 **읽는 자리에서**
보인다. 여정 신선도(specs/13)와 같은 계열의 UX.

## 3. 근본 개선 — 볼트 버전 관리 (운영자 결정 필요)

L2는 "우리 도구로 반영한 것"만 남는다. **손으로 고친 변경은 여전히 증발한다.**

| 안 | 방법 | 장점 | 대가 |
|---|---|---|---|
| **A. 사내 private git** | 볼트만 별도 리포(공개 레포와 분리 유지) | 완전한 이력·blame·복원 | 리포 하나 더 운영, 보안 검토 |
| **B. 스냅샷 아카이브** | 재색인 시점마다 볼트 tar 보관(N개 순환) | 구현 최소, 기존 백업 관례와 동일 | 조문 단위 blame 불가 |
| **C. 현행 유지** | 반영 백업만 | 추가 비용 0 | 손편집 이력 유실 지속 |

⚠ **보안 전제**: 어느 안이든 볼트는 **공개 레포에 들어가지 않는다**(절대 규칙 5).
A안도 사내 전용 원격이어야 한다.

## 4. 하지 않을 것

- **과거 개정 내용 추정·생성** — "2023년엔 이랬을 것"을 LLM이 채우는 순간 규정을 지어내는
  것이다(⛔절대규칙 1). 없으면 **없다고 표시**한다.
- **git 용어 노출** — 커밋·브랜치·해시는 행정 담당자의 언어가 아니다. "언제 · 무엇이 · 어떻게"만.
- **전체 문서 diff를 기본 화면에** — 651줄 통짜 diff는 읽히지 않는다. **바뀐 조문 단위**로 접는다.
- **개정 알림 남발** — 여정 신선도가 이미 "달라졌을 수 있다"를 말한다. 중복 경보 금지.

## 5. 권고 순서 (구현 현황 2026-08-12: L1·L2·L3 완료)

```
L1 타임라인 ✅ (now.tsx ●/○ 타임라인 — d0c7925)
   ↓
L2 diff 상세 ✅ ('전문 보기' — 백업↔현재 줄 다중집합 diff, vault.ts _fullDiff)
   ↓
L3 문서 내 표시 ✅ (문서 드로어 상단 '📌 최근 개정' 띠 — docdata recentChange)
   ↓
근본(A/B/C 중 선택 — 운영자 결정, 미결)
```

구현 중 실측 교훈 2건:
- **백업 매칭은 로그가 정본** — 백업 파일명의 날짜는 *반영일*, 타임라인 이벤트는 *시행일*이라
  파일명 날짜 매칭이 항상 어긋난다(08-03 ↔ 08-05 실측). `corpus_replace_log.jsonl`의
  `backup` 필드로 직접 찾는다(`_backupFor`).
- **전문 diff는 양쪽 다 원시 파일로** — 렌더용 body는 위키링크가 해석돼 링크 있는 줄이
  전부 가짜 diff가 된다. 백업·현재 모두 raw에서 프론트매터만 벗겨 비교.

**L1이 가장 값싸고 효과가 크다**: 지금 카드는 "위임전결규정 · 2026.08.03" 한 줄인데,
타임라인만 돼도 "이 규정은 최근 몇 해간 몇 번 바뀌었고 마지막은 부칙 신설"까지 읽힌다.

## 6. 열어둔 질문

- **백업 누적 정책**(specs/15 §13 미해결) — 반영마다 1개씩 쌓인다. L2가 백업을 소비하기
  시작하면 **보존 기간이 곧 이력의 길이**가 된다. 함께 정해야 한다.
- **마커 커버리지 437/1,943(22%)** — 나머지는 마커 자체가 원문에 없다. 타임라인이
  "개정 이력 없음"으로 보이는 문서가 다수일 텐데 그 표현을 어떻게 할지.
- 조문 단위 blame(어느 조를 언제 누가)까지 갈지, 문서 단위로 충분한지.
