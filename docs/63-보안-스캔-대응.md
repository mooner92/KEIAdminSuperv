## 2. 실제로 위험했던 것 — 로그인 게이트 우회 (F2/F5/F6)

`docs/44`가 세운 fail-closed 게이트가 **사실상 무력했다.**

원인은 한 줄로 말하면 **인가와 서빙이 서로 다른 경로를 봤다**는 것이다.

```js
// web/server.js (수정 전)
if (!authed && !isPublicPath(pathname))        // ← 원본(디코드만 된) 경로로 판정
  return send(res, 302, null, { Location: "/" });

const safe = path.normalize(pathname)…          // ← 정규화된 경로로 파일을 연다
```

그래서 비로그인 요청

```
GET /_next/static/../../d/<규정문서>.html
```

는 공개 허용목록 `/^\/_next\/static\//` 에 걸려 게이트를 **통과한 뒤**, 정규화되어
`out/d/<규정문서>.html` 을 익명에게 그대로 내줬다. `/fonts/`·`/_next/data/` 등
모든 공개 프리픽스가 같은 열쇠로 쓰인다.

### 실측

| 요청(비로그인) | 조치 전 | 조치 후 |
|---|---|---|
| `/_next/static/../../404.html` | **200** — 본문 유출 | 302 |
| `/_next/static/..%2f..%2f404.html` | **200** | 302 |
| `/fonts/../404.html` | **200** | 302 |
| `/404.html` (직접) | 302 | 302 |

같은 파일인데 직접 요청은 302, 우회 경로는 200 — 게이트가 우회된다는 결정적 증거다.

### 함께 드러난 가용성 결함 (F15/F19/F20)

재현 테스트를 짜다가 **확장자 없는 한글 URL 하나로 서버 프로세스가 죽는 것**을 발견했다.
디코드된 한글 슬러그(코드포인트 > 0xff)를 그대로 `Location` 헤더에 실어
`ERR_INVALID_CHAR`가 던져진 것이다. 인증이 필요 없다.

```
GET /d/%ea%b7%9c%ec%a0%95   → ERR_INVALID_CHAR → 프로세스 종료
```

테스트에서 익명 요청 1건이 서버를 내리자 **이후 로그인 사용자 요청이 전부 실패**했다.
NUL(`%00`)은 `fs.stat`을 던지고, CR/LF는 응답 분리로 이어졌다.

### 조치

**정규화 → 인가 → 서빙** 순서로 교정하고, 이후 단계는 정규화된 하나의 경로만 본다.
제어문자는 400으로 거부하고, `Location`은 `encodeURI`로 재인코딩한다.

회귀 = `web/verify-gate-bypass.mjs` — 서버를 **임시 디렉터리에 복사해** 띄우고 raw
소켓으로 공격 경로를 쏜다(실제 `web/out/`을 오염시키지 않는다). 20/20.

## 3. 나머지 조치

### 내부 콘텐츠 차단 가드가 열려 있었다 (F11)

⛔절대 규칙(내부 규정을 공개 레포에 올리지 않는다)의 **마지막 방어선**이다.

git은 기본(`core.quotepath=true`)으로 비ASCII 경로를 따옴표+8진 이스케이프로 낸다:

```
KEI-행정가이드/급여규정.md → "KEI-\355\226\211\354\240\225…/\352\270\211\354\227\254…md"
```

`^KEI-행정가이드/` 정규식이 **영영 매치되지 않는다.** 볼트를 통째로 커밋해도 CI 가드와
pre-commit 훅이 모두 "OK"를 냈다.

지금까지 무사했던 이유가 중요하다 — 이 레포에 `core.quotepath=false`가 걸려 있어서다
(CLAUDE.md에 기록된 설정). 그건 **이 머신의 설정**일 뿐이고,

- CI 체크아웃에는 없다 → 항상 fail-open
- 새로 clone한 머신에도 없다 → 훅도 fail-open

즉 **정작 필요한 환경에서만 꺼져 있었다.** `-z`로 따옴표 없이 원본 경로를 읽도록 고쳤다.
회귀 = `scripts/verify-content-guard.sh` (조치 전 2/4 → 후 4/4).

테스트는 양쪽 다 통과 = 기존 동작 안 깨짐).

### 기타 (F14/F22/F8)

- **F14** — `app.db`가 0644(누구나 읽기)였다. 담긴 것은 bcrypt 해시와 전 사용자 채팅 전문.
  같은 디렉터리의 `.app_secret`은 이미 0600인데 정작 더 민감한 DB가 느슨했다.
  → `init_db`에서 `app.db`/`-wal`/`-shm`을 0600으로 교정(멱등).
- **F22** — dev가 가입 인증 코드를 HTTP 응답에 담아 돌려줬다(`APP_DEV_ECHO_CODE=1`).
  dev는 LAN 바인딩이라 같은 망의 누구나 남의 주소로 가입 요청 → 코드 확인 → 계정 활성화가
  가능했다. → **루프백 요청에만** 코드를 동봉(E2E는 같은 호스트에서 돌므로 영향 없음).
- **F8** — `eval/ab/` 20개 파일(RAG 답변 전문 — 규정 인용·화면 식별자)이 추적 중이었다.
  → 추적 해제 + `.gitignore`.

### 오토픽스 — 부분 완화 (F7/F10/F16/F21) ⚠

`AUTOFIX_ENABLED=1`이 dev에 **실제로 켜져 있다.** 이론이 아니다.

- 제보 본문(의견함 = 아무나 입력)이 무인 에이전트 프롬프트에 그대로 붙었다
  → `_wrap_untrusted()`로 울타리를 치고 '지시가 아니라 신고 내용'임을 명시.
- 관문(`gate_python`/`gate_web`)이 **에이전트가 쓴 코드를 실행**했다.
  `tools/test_*.py`·`web/package.json`이 금지구역에 없어, 에이전트가 자기 검사기를
  먼저 고쳐 놓고 검사받을 수 있었다 → 이 경로들의 변경을 관문 실행 전에 폐기.

**닫히지 않은 부분:** `gate_python`이 도는 테스트는 여전히 worktree의 `tools/*.py`를
import한다. **오토픽스의 목적 자체가 그 파일들을 고치는 것**이므로 구조는 그대로다.
실질적 봉쇄는 **관문을 컨테이너에서 돌리는 설계 변경**뿐이다.
그 전까지는 `AUTOFIX_ENABLED=0`을 권한다.

## 5. 스캔이 놓친 것 — dev 계정 14개 (가장 실질적이었다)

병합 작업 중 dev 트리를 훑다가 발견했다. **스캔은 main에서 돌아 dev 전용 파일을 못 봤다.**

해시 대조 결과 dev 계정 23개 중 **14개가 공개 레포의 평문 비밀번호로 열렸다:**

| 비밀번호 | 계정 |
|---|---|
| `test1234` | `b6test`(26개 스크립트가 사용), `badgetest`, `fmttest`, `integritytest`, `approvalchat`, `imetest`, `fb_test`(10개) |
| `pw1234` | `apprtest_*` 5개 |
| `pw123456` | `apprtest_*` 2개 |

관리자는 없었고 prod는 깨끗했다. 영향은 "같은 LAN에서 dev 테스트 계정으로 로그인해
그 계정 채팅을 열람" 수준이다.

### 아이러니

**스캔이 HIGH로 올린 것은 죽은 비밀번호였고, 진짜 살아있던 것은 스캔이 아예 안 봤다.**
스캔 범위(main)와 실제 운영 표면(dev 포함)이 어긋나면 이런 사각이 생긴다.
다음 스캔은 dev 브랜치도 대상에 넣어야 한다.

### 조치

1. 찌꺼기 `apprtest_*` 7개 삭제 — 채팅·피드백 등 소유 레코드까지. 23개 → 16개.
2. 상주 픽스처 7개 비밀번호 회전 — `tools/.test_credentials`(0600, gitignore)의 무작위 값.
3. 검증 스크립트 46개의 비밀번호 리터럴 제거 — env 주입, **기본값 없음**(미설정 시 종료코드 2).
   아이디는 비밀이 아니므로 그대로 둔다.

```bash
set -a; . tools/.test_credentials; set +a
node web/verify-*.mjs
```

**결과: 레포의 평문 비밀번호로 열리는 계정 14개 → 0개.**

  — 배너가 애초에 없으니 "안 보인다"가 자동으로 참이 된다. 없는 것을 검사하는 테스트는
  통과해도 아무것도 보장하지 않는다. v2 기준으로 다시 쓰거나 폐기해야 한다.
  (패치노트 자체는 `/changelog` 페이지에 정상 게시된다 — 배너 경로만 사라진 것.)

## 11. 백업 점검 (2026-07-29, 이력 정리 후속)

이력 정리를 마치고 백업 안내서(`docs/10-operations.md` §10.5)를 실제 구조에 맞추다가
두 가지가 나왔다. 둘 다 스캔 범위 밖이었다.

### ⓐ app.db 백업이 0644 — 같은 실수 **세 번째**

오늘 F14로 `tools/app.db`를 0600으로 잠갔는데, **매일 03:10 크론이 0644 사본을 만들고
있었다.** 14일치 30개가 타인 읽기 가능 상태였다(전 사용자 채팅 + bcrypt 해시).
`.app_secret`은 `chmod 600`을 하면서 `app.db`만 빠져 있었다.

이 프로젝트에서 **원본은 막고 사본이 새는** 패턴이 반복된다:

| # | 원본 | 새던 사본 |
|---|---|---|
| 1 | `eval/question_bank.jsonl` (gitignore) | `.bak` (F4) |
| 2 | `tools/app.db` (gitignore) | `app.db.pre-prod-*` |
| 3 | `tools/app.db` (0600) | `~/kei-backups/app-*.db` (0644) |

→ 기존 30개 즉시 교정 + 스크립트에 **삼중 방어**(umask 077 · 생성 직후 chmod ·
   실행 끝 전체 재검사 백스톱). 백스톱은 첫 실행에서 실제로 14개를 잡았다.

### ⓑ 볼트가 백업되지 않고 있었다 — 더 심각하다

**마크다운 710개(9.9MB), 이 프로젝트의 진실원천 전체에 백업이 없었다.**

- gitignore됨(공개 레포라 당연·올바름)
- `~/kei-backups/`에 없음 · Syncthing 없음 · 크론 없음
- 유일한 사본인 dev 워크트리는 **같은 디스크** — 백업이 아니라 같은 고장 범위의 복사본

문서에는 "`git = 진실원천`(사내 리모트/미러)"로 적혀 있었으나 **그 미러는 존재하지 않았다.**
아래 TODO로 미확정 표시만 되어 있었고, 그 사이 문서는 "백업되고 있다"는 인상을 줬다.

이게 보안 결함들보다 위험할 수 있다. chroma·out은 볼트에서 재생성되지만
**볼트는 어디서도 재생성되지 않는다** — HWP 변환 + 사람 검수 + 가이드 집필의 결과물이다.

→ `backup-appdb.sh`에 볼트(매일, ~1.9MB)와 원본 HWP·연구자료(월 1회, ~86MB) 추가.
   **복원까지 검증**: md 710개 → 710개 일치, 한글 파일명 보존, 무작위 파일 내용 일치,
   `app-prod.db` integrity ok.

### 남은 위험 — 같은 디스크

백업이 **같은 호스트·같은 디스크**(`/dev/sda3`)에만 있다. 디스크가 죽으면 원본과 백업이
함께 사라진다. 사외/별도 디스크 복제는 여전히 미해결이고, 볼트가 재생성 불가 자산이므로
**다음 우선 과제**다.

### 교훈

**"백업 대상"이라고 적혀 있다고 백업되는 것은 아니다.**
문서의 표는 의도를 적은 것이었고, 실제 산출물을 `ls`로 확인하기 전까지 아무도 몰랐다.
§7-⑴("라벨이 아니라 실물을 열어야 한다")이 백업에도 그대로 적용된다.

## 12. 후속 작업 (2026-07-29)

§7의 교훈을 실제 코드에 반영한 항목들.

### 금액 전결 판정 — 확신에 찬 오답

```
find_tasks('도서 300만원어치 구입하려면 전결권자가 누구야')
  → 1위 '… 물품구입 및 매각(도서포함) > **매각**'
```

별표는 한 상위업무 밑에 반대 leaf를 붙이는데(`> 구입` / `> 매각`) 경로 대부분이 겹쳐
점수가 사실상 동점이 됐고, **순서는 키 문자열이 갈랐다.** rag_core는 `tasks[0]`을 그대로
"전결권자는 X"라는 단정 블록으로 내보내므로, 구입/매각 선택이 우연이었던 셈이다.

→ 형제 배제 + leaf 가중치 + **모호성 가드**(1·2위 동점이면 판정 라우팅을 접고 일반 회수로).
   회귀 = `tools/test_amount_leaf.py`(조치 전 4/8 → 후 8/8).

### 낡은 검증의 '공허한 통과'

v2 이후 실패하던 3건은 **전부 테스트가 낡은 것이고 제품은 멀쩡했다.**
확인 과정에서 세 번 성급하게 결론냈고 매번 실물을 열어보고서야 바로잡았다:

| 내가 처음 내린 결론 | 실제 |
|---|---|
| "검수상태 데이터가 없다" | 키 이름이 `reviewed`였다. 데이터는 정상 |
| "v2가 새로워진 점 배너를 제거했다" | **사이드바 카드로 이동**했다. 기능 정상 |
| "footer 기준일이 사라졌다" | 워딩이 '규정집'→'문서'로 바뀌었다(대장 #86) |

⚠ 가장 위험했던 건 실패가 아니라 **통과**였다. verify-changelog의 2건이
'없는 문자열의 부재'를 확인하고 있어서 **기능이 죽어도 초록불이 뜨는** 상태였다.
판정을 요약문 실물·헤더 집계 같은 **계약**으로 바꿔, 표현이 또 바뀌어도 낡지 않게 했다.

또 하나: 답변 완료 신호(`button[title="도움이 됐어요"]`)가 **복원된 이전 대화의 메시지**에도
있어서, 새 답변이 '문서 검색 중…'인데 즉시 통과했다. **스크린샷으로만 보였다** — grep으로는
끝까지 안 보였을 결함이다.

### 인덱스 신선도 검사 — 조용한 실패 잡기

`tools/index_freshness.py` 신설. 01n이 며칠간 0건을 내놓는데 아무도 몰랐던 사건의 재발 방지다.
**"에러 없이 빈 결과"가 가장 위험한 실패**다 — 아무 알람도 울리지 않고 낡은 값이 계속 서빙된다.

검사: 파일 없음 · 0건(사유 있는 것만 허용) · 직전 대비 30% 이상 급락 · 볼트 대비 2주 이상 지연.
