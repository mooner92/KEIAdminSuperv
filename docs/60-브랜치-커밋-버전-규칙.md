> 사용자 확정: "main 밑에 dev, dev 밑에 기능별 브랜치 + 커밋 규칙 + v1.x.x 버전 관리."

## 1. 브랜치 구조

```
main ──────────●────────●──▶   운영(3101/9001, kei-dev-0703 워크트리). 승격 시에만 병합+태그
  └ dev ───●──●──●──●──●──▶   테스트·통합(3100/9000, /KEIAdminSuperv). 항상 배포 가능 상태 유지
      ├ feat/<기능명>          기능 개발(예: feat/deadlines, feat/reader-glass)
      ├ fix/<이슈>             버그 수정
      └ chore/<작업>           설정·정비
```

> ⚠ **2026-10-08 서버 역할 교체**(§6): 사용자에게 공유된 링크가 3101이라 **3101이 운영, 3100이 테스트**가
> 됐다. 데이터는 옮기지 않았다(3101이 쓰던 app.db·볼트·chroma가 곧 운영 데이터). 아래 표기는 교체 후 기준.

- **main** = 운영 그 자체. 직접 커밋 금지 — `dev → main` 병합(승격)으로만 갱신. 병합 시 태그.
- **dev** = 3100(테스트)에서 굴러가는 통합 브랜치. 기능 브랜치의 병합 대상.
- **기능 브랜치** = `dev`에서 분기 → 개발·검증 → `dev`로 병합(가급적 `--no-ff`로 이력 보존) → 삭제.
  이름: `feat/`·`fix/`·`chore/` + 짧은 영문 케밥(예: `feat/quality-board`).
- 워크트리 운용(교체 후): `kei-dev-0703`=**main 고정(운영)**, `/KEIAdminSuperv`=**dev(테스트)** — 기능 브랜치는 `/KEIAdminSuperv`에서 checkout.
- **push**: dev는 수시 push(백업·공유), main은 승격 시 push. SSH(`git@github.com:mooner92/…`)만
  ([[git-push-auth]] — HTTPS 자격증명 없음). ⛔ 볼트·rule_files 등 내부 데이터는 계속 gitignore
  ([[data-separation-security]]).

## 2. 커밋 규칙 (Conventional Commits 변형)

형식: `<type>(<scope>)?: <제목>` — 제목은 한국어 OK. 본문·푸터 자유.

| type | 용도 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서만 |
| `refactor` | 동작 불변 구조 개선 |
| `perf` | 성능 |
| `test` | 테스트·검증 스크립트 |
| `chore` | 설정·의존성·잡무 |
| `build` / `ci` | 빌드·CI |
| `style` | 포맷(로직 불변) |
| `revert` | 되돌림 |
| `polish` / `refine` | UI·UX 다듬기(이 레포 관례 유지) |
| `harden` | 보안 강화(〃) |

- 강제: `.githooks/commit-msg` 훅(위반 시 커밋 거부). `git config core.hooksPath .githooks` 필요
  (pre-commit gitleaks와 동일 경로 — 이미 설정돼 있음).
- scope는 선택(예: `feat(deadlines):`), 파괴적 변경은 `!`(`feat!:`) + 본문에 설명.
- Merge/Revert/fixup 자동 메시지는 훅이 통과시킴.

## 3. 버전 (v1.x.x)

- **MAJOR(1)**: 서비스 정체성 수준 개편(당분간 1 고정).
- **MINOR(x)**: `dev → main` 승격마다 +1 — 기능 묶음 릴리스. 승격 커밋에 태그 `v1.X.0`.
- **PATCH(x)**: 승격 사이 main에 직접 들어가는 긴급 수정(hotfix)만 +1(`v1.X.Y`).
- 태그는 annotated: `git tag -a v1.2.0 -m "KRDS 전면 개편 + …"` → `git push origin --tags`.
- ⚠ 태그는 **코드만** 스냅샷 — 실제 prod 복원은 태그 + 데이터(볼트·chroma·app.db) 백업 세트
  ([[dev-prod-two-servers]] 승격 절차 참조).

## 4. 승격(릴리스) 절차 요약
> 교체 후(2026-10-08) 절차: 두 워크트리가 저장소 하나를 공유하므로 **main을 갱신해도 운영 트리 파일은
> 저절로 바뀌지 않는다** — 운영 트리(`kei-dev-0703`, main)에서 직접 병합한다.
> ```bash
> cd /home/mhchoi/kei-dev-0703 && git merge --no-ff dev -m "merge: v1.X.0 승격 — …" && git tag v1.X.0
> (web 변경 시) cd web && nvm use 22 && NEXT_PUBLIC_BUILD_ID=$(git rev-parse --short HEAD) VAULT_DIR=/home/mhchoi/kei-dev-0703/KEI-행정가이드 npm run build && pm2 reload kei-guide
> (API 변경 시) pm2 restart deploy/ecosystem.prod.config.js --only kei-rag-api  → errored면 pm2 start 같은 인자
> git push origin main --tags  &&  cd /KEIAdminSuperv && git merge main && git push origin dev   # 백머지
> ```
1. dev에서 검증 완료(**3100** 실렌더·평가) → 사용자 승인
2. `main`에 `dev` 병합(--no-ff) → 태그 `v1.X.0` → push(main+tags)
3. 운영 데이터 이관(필요할 때만)·재빌드·재시작(승격 런북: [[dev-prod-two-servers]] gotcha —
   ① PM2 env는 delete+start ② flag 테이블 복제 ③ **APP_DB env 필수**(ecosystem.local.js —
   없으면 rag_core가 플래그를 못 읽어 uplaw·절차팩 등 백엔드 플래그 기능 전부 미발동,
   v1.3.0 승격 실측) ④ 볼트·chroma·tools/index·forms-pdf·quality rsync(백업 선행)
   ⑤ 신규 npm 의존성은 npm install 먼저)
4. **⚠ 백머지(필수) — `main → dev`**: 승격 때 main에서만 생기는 커밋(병합 커밋 + docs/60 이력·
   prod 설정)이 dev로 돌아오지 않으면 두 브랜치가 갈라진다("main is ahead" 표시의 정체).
   ```bash
   git checkout dev && git merge origin/main --no-edit && git push origin dev
   git log --oneline dev..origin/main | wc -l   # 0이어야 정상
   ```
   실측(2026-07-26): v1.4.0~v1.5.1 3회 승격 동안 백머지를 안 해 main에만 6커밋이 쌓였고,
   사용자가 "main이 dev보다 앞서 있다"고 발견. 서비스 영향은 없었지만 이후 분기 브랜치가
   승격 이력 없이 시작되는 혼란이 생긴다.
5. dev는 계속 다음 작업

## 5. 예외·주의
- 훅 우회(`--no-verify`)는 긴급시에만, 사후 정리 필수.
- 기능 브랜치 장기 방치 금지 — dev와 자주 리베이스/병합.
- 옛 브랜치는 2026-10-08 정리 — main·dev만 남기고 나머지는 **`archive/<브랜치명>` 태그로 보존 후 삭제**
  (로컬·원격). 되살리기: `git switch -c <이름> archive/<이름>`.
