# docs/60 — 브랜치 · 커밋 · 버전 규칙 (2026-07-22 확정)

> 사용자 확정: "main 밑에 dev, dev 밑에 기능별 브랜치 + 커밋 규칙 + v1.x.x 버전 관리."

## 1. 브랜치 구조

```
main ──────────●────────●──▶   프로덕션(3100/9000, /KEIAdminSuperv). 승격 시에만 병합+태그
  └ dev ───●──●──●──●──●──▶   통합·검증(3101/9001, kei-dev-0703 워크트리). 항상 배포 가능 상태 유지
      ├ feat/<기능명>          기능 개발(예: feat/deadlines, feat/reader-glass)
      ├ fix/<이슈>             버그 수정
      └ chore/<작업>           설정·정비
```

- **main** = prod 그 자체. 직접 커밋 금지 — `dev → main` 병합(승격)으로만 갱신. 병합 시 태그.
- **dev** = 3101에서 항상 굴러가는 통합 브랜치. 기능 브랜치의 병합 대상.
- **기능 브랜치** = `dev`에서 분기 → 개발·검증 → `dev`로 병합(가급적 `--no-ff`로 이력 보존) → 삭제.
  이름: `feat/`·`fix/`·`chore/` + 짧은 영문 케밥(예: `feat/quality-board`).
- 워크트리 운용: `/KEIAdminSuperv`=main 고정, `kei-dev-0703`=dev(기능 브랜치 작업 시 그 안에서 checkout).
- **push**: dev는 수시 push(백업·공유), main은 승격 시 push. SSH(`git@github.com:mooner92/…`)만
  ([[git-push-auth]] — HTTPS 자격증명 없음). ⛔ 볼트·rule_files 등 내부 데이터는 계속 gitignore
  ([[data-separation-security]]).

## 2. 커밋 규칙 (Conventional Commits 변형)

형식: `<type>(<scope>)?: <제목>` — 제목은 한국어 OK. 본문·푸터 자유.

| type | 용도 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서만 |
| `refactor` | 동작 불변 구조 개선 |
| `perf` | 성능 |
| `test` | 테스트·검증 스크립트 |
| `chore` | 설정·의존성·잡무 |
| `build` / `ci` | 빌드·CI |
| `style` | 포맷(로직 불변) |
| `revert` | 되돌림 |
| `polish` / `refine` | UI·UX 다듬기(이 레포 관례 유지) |
| `harden` | 보안 강화(〃) |

- 강제: `.githooks/commit-msg` 훅(위반 시 커밋 거부). `git config core.hooksPath .githooks` 필요
  (pre-commit gitleaks와 동일 경로 — 이미 설정돼 있음).
- scope는 선택(예: `feat(deadlines):`), 파괴적 변경은 `!`(`feat!:`) + 본문에 설명.
- Merge/Revert/fixup 자동 메시지는 훅이 통과시킴.

## 3. 버전 (v1.x.x)

- **MAJOR(1)**: 서비스 정체성 수준 개편(당분간 1 고정).
- **MINOR(x)**: `dev → main` 승격마다 +1 — 기능 묶음 릴리스. 승격 커밋에 태그 `v1.X.0`.
- **PATCH(x)**: 승격 사이 main에 직접 들어가는 긴급 수정(hotfix)만 +1(`v1.X.Y`).
- 태그는 annotated: `git tag -a v1.2.0 -m "KRDS 전면 개편 + …"` → `git push origin --tags`.
- ⚠ 태그는 **코드만** 스냅샷 — 실제 prod 복원은 태그 + 데이터(볼트·chroma·app.db) 백업 세트
  ([[dev-prod-two-servers]] 승격 절차 참조).

## 4. 승격(릴리스) 절차 요약
1. dev에서 검증 완료(3101 실렌더·평가) → 사용자 승인
2. `main`에 `dev` 병합(--no-ff) → 태그 `v1.X.0` → push(main+tags)
3. prod 데이터 이관·재빌드·재시작(승격 런북: [[dev-prod-two-servers]] gotcha 2종 —
   PM2 env는 delete+start, flag 테이블 복제)
4. dev는 계속 다음 작업

## 5. 예외·주의
- 훅 우회(`--no-verify`)는 긴급시에만, 사후 정리 필수.
- 기능 브랜치 장기 방치 금지 — dev와 자주 리베이스/병합.
- `feat/0620`(구 prod)·`feat/krds`·`feat/0703`·`feat/0722`는 **전환기 이력 브랜치** — 보존만,
  신규 작업 금지(신규는 반드시 dev에서 분기).
