# 54 — 모바일 우선 전략 (반응형 단일 앱)

> 결정: **별도 모바일 뷰 트리를 만들지 않는다.** 지금의 정적 export + 반응형 단일 앱을
> 그대로 쓰되, 모바일에서 가장 많이 쓰는 두 흐름만 "우선·매끄럽게" 강화한다.
> 근거: 코드 1벌·유지보수 1곳(DRY), "모든 건 컴포넌트 단위" 원칙과 일치(docs/53).

## 사용 맥락 (실측 가정)
- 사용자는 보통 **전체화면·반절화면**으로 데스크톱에서 쓴다.
- 모바일(웹앱, 추후 Expo 등으로 래핑 가능)에서는:
  - **일반 사용자 → 채팅**이 거의 전부. (홈 `/` = RAG 채팅)
  - **관리자 → AI 자동수정(오토픽스)**이 주 용도. (`/admin` 📮 의견함)
- 나머지 화면은 "간단하게 보이면 충분" — 이미 반응형이라 그대로 둔다.

## 강화 지점 (이 두 흐름만 특별히)
1. **채팅(홈 `/`)** — 모바일 기본 랜딩. 이미 반응형(전 페이지 3뷰포트 감사 통과, 원장 #35).
2. **관리자 의견함(`/admin` → AdminReports)** — 모바일 관리자 주 화면:
   - **모바일 진입 시 기본 탭 = 의견함**(`admin.tsx`: `matchMedia("(max-width:640px)")` + 해시
     없을 때만; 데스크톱은 대시보드 기본 유지). 딥링크(`#reports` 등)는 항상 우선.
   - **접수함 카드·오토픽스 흐름을 모바일에 맞게**(`Feedback.module.css` `@media ≤640px`):
     메모 입력은 한 줄 전폭, `저장`·`🤖 자동 수정`은 아래 한 줄. 상태 셀렉트·접수시각 겹침 방지.
   - **`🤖 자동 수정` 버튼을 시각적으로 특별하게**(`.autofixBtn` accent) — 관리자 핵심 액션이라
     전 뷰포트에서 도드라지게. 동작·가드레일은 docs/52(Phase A)와 동일(격리 브랜치·머지는 사람).

## 하지 않기로 한 것
- `/m/*` 같은 **별도 모바일 라우트/레이아웃 트리** — 화면 2벌·컴포넌트 원칙 상충이라 배제.
- 관리자 **전체 대시보드**의 모바일 특화 — 데스크톱향 유지(모바일에선 의견함이 먼저 뜨므로 무방).

## 검증
- Playwright 모바일(390) 실렌더: 진입=의견함, 가로 오버플로 0, 오토픽스 버튼 5개 화면 내(우측끝 340px).
- 회귀: 데스크톱(1440) 진입=대시보드 유지.
- 향후 Expo/Capacitor 래핑 시 이 반응형 URL을 WebView로 감싸면 즉시 앱화 가능(별도 작업).
