# 33. 사설 아카이브 + 서버 이전 계획 (⛔ 초안, 미승인)

> 사용자 발제(2026-07-13): 추후 다른 서버(사내 다른 장비 또는 외부망/클라우드)로 이전할 때
> 데이터를 한 번에 옮길 수 있도록 **git private 저장소에 전부 아카이빙**하는 운영이 가능한가,
> 가능하면 베스트인가. 이 문서는 순화된 계획(공개 레포용) — 구체 인프라 식별자는 담지 않는다.

## 0. 결론 먼저

**가능하고, 조건 하나를 지키면 사실상 베스트다.** 조건 = **3계층 분리**:
git에 "전부"를 넣는 게 아니라, *넣으면 안 되는 것*을 기계로 막은 상태에서 나머지 전부를 넣는다.

| 계층 | 내용 | 위치 | 근거 |
|---|---|---|---|
| A. 코드 | 앱·파이프라인·순화 스펙 | **공개 GitHub**(현행) | 이미 데이터 분리 규율 확립 |
| B. 데이터 | 볼트(규정 md)·원본 문서(HWP/PDF)·평가셋·파생 인덱스 | **신설 private repo 1개** | ~110MB, LFS 불필요. 이력 = 규정 개정 추적 보너스 |
| C. 반출 금지 | 사용자 채팅 DB(app.db)·세션 서명키·개인정보 | **어떤 git에도 금지** | 개인정보·비밀키는 저장소 이력에 남으면 회수 불가 |

- 실측 크기: 볼트 ≈5.4MB · 원본 문서 ≈97MB · 평가+인덱스 ≈5MB → **합계 ≈110MB** (GitHub
  단일 파일 100MB 제한에 걸리는 파일 없음 — LFS 없이 시작 가능).
- 제외해도 되는 것: 벡터DB(≈311MB)와 모델은 **재생성/재다운로드 가능** — 아카이브 대상 아님
  (이전 절차에서 재구축, §4).

### 솔직한 고지(사용자 판단 존중, 기록만)
내부 규정 문서를 외부 클라우드(GitHub private)에 두는 것은 기관 정보보안 지침의 확인을
권장한다. 사용자 판단("기밀 아님")을 전제로 진행하되, 우려가 생기면 완화 옵션이 있다:
ⓐ private repo 접근 = SSH 키 + 2FA 계정 한정 ⓑ `git-crypt`/`age`로 볼트 디렉터리만 암호화
커밋 ⓒ 대안: 사내 다른 장비에 bare repo(`git init --bare`)를 두고 push(클라우드 완전 회피).
**C계층(개인정보)은 이 논의와 무관하게 어떤 경우에도 git 금지.**

## 1. private repo 구조 (신설 1개)

```
KEI-admin-archive (private)
├─ vault/        ← KEI-행정가이드 전체 (Syncthing과 병행: git=이력·복원, Syncthing=실시간 동기화)
├─ sources/      ← 원본 문서(규정 HWP/HWPX, 연구행정 PDF/PPTX)
├─ eval/         ← 골든셋·평가 리포트
├─ index/        ← tools/index 파생물(재생성 가능하지만 이력 편의상 포함)
├─ MANIFEST.md   ← 각 디렉터리의 원 위치·복원 방법·"여기 없는 것"(C계층·재생성물) 목록
└─ .gitignore    ← *.db, *.sqlite*, .app_secret*, *.key, chroma/ — 3중 방어의 1차
```

## 2. 실수 방지 장치(핵심 — "전부 아카이빙"이 안전한 이유)

1. `.gitignore`: C계층 패턴 원천 차단.
2. **pre-push 가드**(훅 또는 push 스크립트 내 검사): 스테이징에 `app.db|.app_secret|*.key|
   비밀번호 해시 패턴`이 잡히면 push 중단. *가드 자체를 테스트*(금지 파일 커밋 시도 → 차단 확인).
3. push 스크립트 단일 경로: `archive_push.sh` — rsync(볼트·인덱스·평가) → 변경 요약 커밋
   메시지 자동 생성 → 가드 → push. 수동 실행 기본, 원하면 cron 일 1회.

## 3. 운영 방식

- 평시: 볼트·평가·인덱스가 바뀐 날 `archive_push.sh` 1회(또는 cron). 커밋 이력이 곧
  "규정집 개정 이력 + 파이프라인 산출 이력"이 된다.
- 공개 repo와의 관계: 코드 커밋(공개)과 데이터 커밋(사설)이 분리 — 지금의 데이터 분리
  규율은 그대로, 오히려 백업이 생겨 강화된다.

## 4. 서버 이전 런북 (요약)

1. **새 서버에서 clone 2개**: 공개(코드) + 사설(데이터) → `vault/`·`sources/`를 제 위치에 배치.
2. **C계층 수동 이동**: 채팅 DB 백업 + 세션 서명키를 `age`/`gpg` 암호화 tar로 만들어
   직접 전송(scp 등) → 복호화 배치. (이전을 기회로 서명키 재발급도 선택지 — 전 사용자
   재로그인 1회 발생.)
3. **재생성물 재구축**: 임베딩 모델·LLM(GGUF) 재다운로드(또는 대용량 번들 직접 복사) →
   `02_chunk_and_embed.py`로 벡터DB 재색인 → Node/venv 재설치 → web 빌드.
4. **환경 이식**: PM2 ecosystem env(관리자 목록·SMTP·포트), 리버스 프록시/Zero Trust 재설정.
5. **검증 스위트**: health → 골든셋(무회귀 기준선 비교) → 신뢰 게이트 E2E → Playwright 스모크.
6. **외부망/클라우드로 갈 경우 추가**: HTTPS 전환(세션 쿠키 secure), 접근제어 재구성(ZT/VPN),
   그리고 **규정 데이터 반출·개인정보 이전에 대한 기관 승인**(이건 기술이 아니라 절차).

## 5. 수용 기준

ⓐ 가드 테스트: 금지 파일을 고의로 스테이징 → push 차단 실증
ⓑ 재구축 리허설: 새 디렉터리에서 clone 2개 + 런북만으로 dev 스택 기동(문서 완결성 증명)
ⓒ MANIFEST와 실제 내용 일치(스크립트 검사) ⓓ 아카이브에 C계층 파일 0개(전수 스캔).

## 6. 순서 제안

① private repo 생성 + 초기 push(B계층) → ② 가드·`archive_push.sh` + 수용 ⓐⓓ →
③ MANIFEST·런북 확정 → ④ 재구축 리허설(수용 ⓑ) — 이전이 실제로 잡히기 전에 ④까지
끝내두면 이전 당일은 "런북 실행"만 남는다.
